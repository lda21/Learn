What is ClickHouse?

  • An open-source, column-oriented database management system (DBMS) built for online analytical processing (OLAP)
  • Designed for real-time analytics over huge datasets — aggregations and filters across billions of rows in milliseconds
  • Uses vectorized query execution and aggressive compression to process data at extreme speed
  • Speaks a rich, SQL dialect with hundreds of built-in functions, and exposes HTTP and native protocols plus JDBC/ODBC
  • Originated at Yandex to power web analytics; now a standalone company (ClickHouse Inc.) and a thriving open-source project under the Apache 2.0 license
-- A billion-row aggregation that returns in well under a second
SELECT country, count() AS hits, avg(duration_ms) AS avg_ms
FROM web_events
WHERE event_date >= today() - 7
GROUP BY country
ORDER BY hits DESC
LIMIT 10;

Why columns win for OLAP

  • Queries touch only the columns they reference — far less I/O
  • Values of one column share a data type, so they compress brilliantly
  • Tight columns fit in CPU cache and feed SIMD-friendly loops

Vectorized execution

  • ClickHouse processes data in blocks of many rows at once, not row-by-row
  • Each operator runs over whole arrays, exploiting SIMD CPU instructions
  • Result: high throughput and excellent cache utilization

Row stores are optimized to read and write whole rows (great for OLTP). Column stores are optimized to scan a few columns across millions of rows (great for analytics).

Architecture Overview

MergeTree engine

The core table engine family. Data is stored sorted by the ORDER BY key and written as immutable parts that merge in the background.

Parts & granules

Each part holds columns split into granules (default 8192 rows). Granules are the unit the sparse index points to.

Sparse primary index

One index entry per granule, not per row. The index is tiny and lives in memory, letting ClickHouse skip whole ranges of data.

Shards & replicas

Scale out by sharding (split data across nodes) and ensure durability with replicas (copies kept in sync).

ClickHouse can run as a single binary on a laptop or as a large distributed cluster — the same engine, the same SQL.

Creating Tables & MergeTree

CREATE TABLE web_events
(
    event_date  Date,
    event_time  DateTime,
    user_id     UInt64,
    country     LowCardinality(String),
    url         String,
    duration_ms UInt32
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)   -- coarse data chunks for pruning/TTL
ORDER BY (country, event_time, user_id);  -- sort key = primary index
  • ORDER BY defines the sort order of data on disk and, by default, the primary key (sparse index)
  • PARTITION BY groups parts into partitions — usually by month or day — enabling fast pruning and easy data drops
  • Choose an ORDER BY that matches your most common filters; it is the single biggest performance lever

Data Types

Scalars

  • Int8..Int256, UInt8..UInt256
  • Float32, Float64, Decimal(P, S)
  • String, FixedString(N)
  • Date, Date32, DateTime, DateTime64
  • Bool, UUID, Enum8 / Enum16

Composite & special

  • Array(T) — e.g. Array(String)
  • Tuple(...), Map(K, V), Nested
  • Nullable(T) — adds a NULL bitmap (costs space)
  • LowCardinality(T) — dictionary-encode repeated values
  • JSON, IPv4 / IPv6, geo types

LowCardinality dramatically shrinks columns with few distinct values (countries, statuses, event names) and speeds up filters & GROUP BY. Prefer non-Nullable columns where you can.

MergeTree Engine Deep Dive

INSERT
→
New part
(sorted)
→
Background
merge
→
Fewer, larger
parts
  • Each insert creates a new immutable part; data inside a part is sorted by the ORDER BY key
  • A background process continuously merges small parts into larger ones (the "Merge" in MergeTree)
  • Columns are stored in granules (index_granularity, default 8192 rows); the sparse primary index stores one mark per granule
  • A query uses the index to find candidate granules, then reads only those — skipping the rest of the part

Because parts are immutable and merges are async, ClickHouse favors large batch inserts over many tiny ones — too many small parts hurts performance.

MergeTree Family Variants

EngineWhat it does on mergeUse case
MergeTreeJust sorts & merges partsGeneral analytics
ReplacingMergeTreeKeeps the last row per sort key (optional version col)Deduplication / upserts
SummingMergeTreeSums numeric columns for rows with the same keyPre-aggregated counters
AggregatingMergeTreeMerges aggregate states (-State / -Merge)Materialized-view rollups
CollapsingMergeTreeCancels +1 / -1 rows by a sign columnMutable state via inserts
VersionedCollapsingCollapsing with an explicit versionOut-of-order updates

Each Replicated* counterpart (e.g. ReplicatedMergeTree) adds replication via ClickHouse Keeper. Note: deduplication/collapsing happens at merge time — use FINAL or aggregation to get fully merged results at query time.

Inserting Data

-- Batch insert: prefer thousands+ of rows per INSERT, not one at a time
INSERT INTO web_events VALUES
  ('2026-06-09', '2026-06-09 10:00:00', 42, 'US', '/home', 120),
  ('2026-06-09', '2026-06-09 10:00:01', 43, 'DE', '/pricing', 85);

-- Load files directly in many formats
INSERT INTO web_events FORMAT CSV               -- or CSVWithNames
INSERT INTO web_events FORMAT JSONEachRow        -- one JSON object per line
INSERT INTO web_events FROM INFILE 'data.parquet' FORMAT Parquet;

Batching is the rule

Each INSERT becomes a part. Aim for large batches (tens of thousands of rows) to avoid the "too many small parts" problem.

Async inserts

Set async_insert=1 and ClickHouse buffers many small client inserts server-side, flushing them as one part — ideal for many concurrent writers.

Querying & SQL Dialect

SELECT
    country,
    toStartOfHour(event_time) AS hour,
    count()                   AS hits,
    uniq(user_id)             AS visitors
FROM web_events
WHERE event_date = today()
GROUP BY country, hour
HAVING hits > 100
ORDER BY hits DESC
LIMIT 5 BY country;          -- ClickHouse extension: top-5 per country
  • Standard SQL: SELECT, WHERE, GROUP BY, JOIN, HAVING, window functions, CTEs
  • Extensions: LIMIT n BY expr, ARRAY JOIN, WITH ROLLUP/CUBE, lambda & higher-order array functions
  • Rich helpers for dates (toStartOfHour), arrays, strings, JSON, URLs, and approximate analytics

Aggregate Functions & Combinators

SELECT
    count()                          AS total,
    sum(duration_ms)                 AS total_ms,
    uniq(user_id)                    AS approx_unique,    -- fast approximate
    uniqExact(user_id)               AS exact_unique,
    quantile(0.95)(duration_ms)      AS p95,
    avgIf(duration_ms, country = 'US') AS us_avg,         -- -If combinator
    sumArray(values)                 AS sum_of_arrays     -- -Array combinator
FROM web_events;
  • Combinators are suffixes that transform any aggregate function:
  • -If applies a condition; -Array operates on array elements; -Merge / -State handle intermediate aggregate states
  • -State produces a partial aggregate you can store; -Merge combines those states later — the foundation of incremental rollups

Materialized Views

A ClickHouse materialized view is an insert trigger: as rows land in the source table, the view's query runs on that block and writes results into a target table — incremental aggregation, no scheduled batch job.

-- Target: hourly rollups using aggregate states
CREATE TABLE hits_by_hour
(
    hour DateTime,
    country LowCardinality(String),
    hits AggregateFunction(count),
    visitors AggregateFunction(uniq, UInt64)
) ENGINE = AggregatingMergeTree ORDER BY (hour, country);

CREATE MATERIALIZED VIEW mv_hits TO hits_by_hour AS
SELECT toStartOfHour(event_time) AS hour, country,
       countState() AS hits, uniqState(user_id) AS visitors
FROM web_events GROUP BY hour, country;

-- Query: merge the states back into final numbers
SELECT hour, country, countMerge(hits), uniqMerge(visitors)
FROM hits_by_hour GROUP BY hour, country;

Projections & Skip Indexes

Data-skipping indexes

Secondary indexes that let ClickHouse skip granules that cannot match a filter.

  • minmax — min/max per block
  • set(N) — small distinct sets
  • bloom_filter — membership tests
  • ngrambf_v1 / tokenbf_v1 — text search

Projections

An alternate physical ordering or pre-aggregation of the same table, stored inside it. The optimizer picks the projection automatically when it speeds a query up.

ALTER TABLE web_events ADD INDEX url_bf url
  TYPE bloom_filter GRANULARITY 4;

ALTER TABLE web_events ADD PROJECTION by_user
  (SELECT * ORDER BY user_id);

Dictionaries

Dictionaries are in-memory key-value lookup structures sourced from external systems (Postgres, MySQL, files, HTTP, another ClickHouse table). They replace many JOINs with a fast dictGet.

CREATE DICTIONARY country_names
(
    code   String,
    name   String
)
PRIMARY KEY code
SOURCE(CLICKHOUSE(TABLE 'countries'))
LAYOUT(HASHED())
LIFETIME(MIN 300 MAX 600);   -- auto-refresh window in seconds

-- Use it like a function — no JOIN needed
SELECT dictGet('country_names', 'name', country) AS country_name,
       count()
FROM web_events
GROUP BY country_name;

Dictionaries are cached in RAM and refreshed on a schedule, so lookups are extremely fast and stay current. Layouts include flat, hashed, complex_key_hashed, and cache.

  • ReplicatedMergeTree keeps copies of data in sync across replicas for high availability and durability
  • ClickHouse Keeper (a faster, built-in alternative to ZooKeeper) coordinates replication and distributed DDL
  • The Distributed engine is a routing layer: it fans queries out to shards and merges results — it stores no data itself
  • Sharding scales capacity & throughput; replication scales availability & read concurrency

TTL & Data Lifecycle

TTL (time-to-live) expressions let ClickHouse automatically delete or move data as it ages — essential for logs and metrics with retention policies.

CREATE TABLE logs
(
    ts   DateTime,
    msg  String
)
ENGINE = MergeTree
ORDER BY ts
TTL ts + INTERVAL 30 DAY DELETE,                 -- drop after 30 days
    ts + INTERVAL 7  DAY TO VOLUME 'cold';        -- tier to cheaper disk

-- Column-level TTL and aggregation-on-expire are also supported
ALTER TABLE web_events
  MODIFY TTL event_date + INTERVAL 90 DAY
  GROUP BY country SET duration_ms = sum(duration_ms);
  • TTL can DELETE rows, move parts between disks/volumes (hot/warm/cold tiers), or roll up data on expiry
  • Dropping a whole partition is the cheapest way to delete large date ranges

Performance Tuning

  • Design the ORDER BY key around your filters — columns you filter on first should lead, low-cardinality first often helps
  • Partition pruning: filter on the partition expression so whole partitions are skipped
  • PREWHERE reads filter columns first to discard granules before reading the rest (the optimizer often applies it for you)
  • Inspect plans with EXPLAIN and profile with system.query_log & EXPLAIN indexes = 1
-- PREWHERE filters cheaply before reading wide columns
SELECT url, duration_ms
FROM web_events
PREWHERE country = 'US' AND event_date = today()
WHERE duration_ms > 1000;

-- See which granules/indexes a query uses
EXPLAIN indexes = 1
SELECT count() FROM web_events WHERE country = 'DE';

Compression & Codecs

General compression

  • LZ4 — default; very fast, good ratio
  • ZSTD — higher ratio, tunable level, a bit more CPU
  • Set per column or as the table/server default

Specialized codecs

  • Delta / DoubleDelta — monotonic / time-series values
  • Gorilla — gauge-like floating point
  • T64 — truncate unused high bits of integers
CREATE TABLE metrics
(
    ts    DateTime CODEC(DoubleDelta, ZSTD(3)),  -- timestamps compress hugely
    value Float64  CODEC(Gorilla),
    host  LowCardinality(String)
) ENGINE = MergeTree ORDER BY (host, ts);

Codecs can be chained: a transform codec (Delta) followed by a general codec (ZSTD) often yields the best ratios.

Observability & System Tables

ClickHouse introspects itself through the system database — everything from running queries to part sizes is queryable with SQL.

System tableWhat it shows

system.partsParts per table: rows, bytes, compression ratio

system.metrics / system.eventsReal-time counters and cumulative events
system.mutationsStatus of ALTER UPDATE/DELETE operations
-- Find the slowest queries in the last hour
SELECT query_duration_ms, read_rows, formatReadableSize(memory_usage), query
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time > now() - INTERVAL 1 HOUR
ORDER BY query_duration_ms DESC LIMIT 10;

ClickHouse Cloud & Ecosystem

Managed service

ClickHouse Cloud runs and scales clusters for you on AWS, GCP, and Azure — backups, upgrades, and security handled.

Storage / compute split

Data lives in object storage; stateless compute scales independently and can idle to zero, so you pay for what you use.

chDB

An embedded, in-process ClickHouse engine (think "SQLite for OLAP") usable from Python and other languages.

Tools

Official clients for Python, Go, Node, Java; clickhouse-client, the Play UI, and BI integrations.

The same open-source engine powers your laptop, a self-managed cluster, and the cloud — skills transfer everywhere.

Best Practices

1 Batch your inserts — thousands of rows per INSERT, never row-by-row
2 Design the ORDER BY key around your real query filters — biggest lever there is
3 Avoid too many small parts; use async inserts for many concurrent writers
4 Use LowCardinality for repetitive string columns (status, country, name)
5 Partition coarsely (by month/day), not by high-cardinality columns
6 Prefer denormalized wide tables and dictionaries over heavy JOINs
7 Don't use ClickHouse for OLTP or frequent single-row updates/deletes
8 Use materialized views with AggregatingMergeTree for incremental rollups
9 Add skip indexes / projections for filters the sort key doesn't cover
10 Monitor with system tables & pick the right codecs per column
