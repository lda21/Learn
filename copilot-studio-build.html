This course follows the loop a maker actually runs — not the architecture, but the clicks, prompts, and gotchas. You build one agent end-to-end, then iterate on it from real usage.

Running example: an IT Helpdesk agent that answers policy questions and opens tickets.

Before You Build: Prerequisites

What You Need

  • A Power Platform environment you can author in
  • A Copilot Studio license or trial seat
  • Maker access (not just end-user) in that environment
  • Knowing your tenant’s DLP policy — it limits connectors

Pick the Right Environment

  • Never build in the Default environment for prod work
  • Use a dedicated Dev environment with Dataverse
  • Environment = boundary for data, DLP, and capacity
  • Confirm spend caps so test loops don’t burn budget

Two minutes choosing the environment saves a painful migration later.

Create Your First Agent

Copilot Studio → Create → New agent

# Describe it in natural language
"You are the Contoso IT Helpdesk assistant. You help
 employees with laptop, VPN, and software-access issues.
 Answer from the IT knowledge base. If you can't resolve
 it, open a ticket in ServiceNow on the user's behalf."

# Copilot Studio drafts:
- A name + icon
- Starter instructions
- Suggested tone
- Sample topics

# You then refine name, description, and instructions.

The describe-it flow is a starting point, not the finished agent — the next slides tighten it.

Writing the Agent’s Instructions

Treat It Like a Prompt

  • State the role and the audience plainly
  • List what it should and should not do
  • Name the knowledge and tools it can rely on
  • Specify tone, length, and escalation rules

Common Mistakes

  • Vague: “be helpful” — gives the model nothing
  • Overloaded: 30 rules the orchestrator can’t weigh
  • No fallback: what to do when it can’t answer
  • Forgetting to say “cite your sources”

Iterate the instructions in the test pane — change one line, re-ask, watch the behavior shift.

Generative vs. Classic Orchestration

Generative (default)

  • The LLM picks topics, knowledge, and tools per turn
  • Best for open Q&A and fuzzy intents
  • You guide it with good descriptions, not rigid graphs
  • Handles multi-step reasoning across tools

Classic / Topic-First

  • Trigger phrases route directly to authored topics
  • Best for deterministic flows (reset password)
  • Predictable, testable, auditable paths
  • Use inside a generative agent for the steps that must not vary

Most real agents are hybrid: generative for answers, topics for the actions that have to be exact.

Building a Topic, Node by Node

Topic: "Open a hardware ticket"

Trigger phrases:  "my laptop is broken", "request new device"

[Trigger]
   → [Question] "What device is affected?"   → var: device
   → [Question] "Describe the issue"          → var: issue
   → [Condition] device is empty?
        — yes → [Message] "I need the device first" → loop
        — no  → [Action] Create ServiceNow ticket(device, issue)
   → [Message] "Ticket {ticket.number} created. ETA 2 days."

Nodes: Question, Condition, Action, Message, Set variable. Build it on the canvas or in YAML.

Variables, Slots & Entities

Variables

Hold values across a conversation. Scope: topic-local or global.

Slot Filling

The agent keeps asking until required inputs are collected.

Entities

Typed extractors — email, date, number, or custom lists.

System Variables

User.DisplayName, Activity.Text, channel, locale — free context.

Tip: let the generative orchestrator fill slots from natural language instead of asking one question per field.

Adding Knowledge That Works

Wire It Up

  • Add source: SharePoint site, files, public URL, Dataverse
  • Give each source a clear description — the router reads it
  • Scope SharePoint to a site/library, not the whole tenant
  • Re-index after big content changes

Quality Levers

  • Clean, well-titled docs beat one giant PDF
  • Permissions are honored — test as a real user
  • Raise the moderation threshold to cut weak answers
  • Turn on citations so answers are auditable

If answers are wrong, the fix is usually the content and scoping, not the model.

Writing Tool & Action Descriptions

# The orchestrator chooses tools by READING their descriptions.
# Write them like instructions to a junior teammate.

Bad:   "ServiceNow action"
Good:  "Create an IT support ticket in ServiceNow. Use this
        when the user has a hardware or software problem that
        you could not resolve from the knowledge base.
        Requires: device (string), issue (string).
        Returns: ticket number + status."

# Same rule for each input parameter:
device:  "The affected device, e.g. 'ThinkPad X1' or 'iPhone 15'."

90% of “the agent didn’t call my tool” is a weak description, not a bug.

Connecting Actions

Prebuilt Connector

Pick ServiceNow / SAP / Jira, sign in, select the operation. Fastest path.

Power Automate Flow

Wrap multi-step logic into one action the agent calls. Inputs → outputs typed.

REST / OpenAPI

Paste a spec — Copilot Studio generates the action and schema for you.

MCP Server

Add a Model Context Protocol endpoint; its tools auto-surface to the agent.

Watch the DLP policy: if the connector is blocked at the environment level, it won’t appear.

Prompt Actions

What They Are

  • Reusable LLM prompts exposed as first-class tools
  • Summarize, classify, extract, rewrite — on demand
  • Built and tested in AI Builder’s prompt editor
  • Typed inputs and outputs, like any other action

When to Reach for One

  • Shape free text into structured data before an action
  • Classify a ticket’s urgency from its description
  • Generate a polished reply from raw notes
  • Keep a tricky prompt in one place, reused everywhere

Prompt actions turn “ask the model nicely” into a versioned, testable building block.

Test Pane & the Activity Map

Test as You Build

  • The test pane re-runs on every save
  • Expand a turn to see the full trace
  • Inspect topic chosen, tools called, inputs, citations
  • “Test as another user” to verify permissions

Read the Trace

  • Which topic or generative path handled the turn?
  • Did the orchestrator pick the right tool?
  • What arguments did it pass?
  • Were knowledge passages actually retrieved?

The trace is the only honest signal — trust it over the chat bubble.

Debugging Common Failures

SymptomLikely Cause & Fix
Agent ignores a toolWeak/absent tool description — rewrite it as instructions
“I don’t know” on known contentSource not indexed, mis-scoped, or moderation too strict
Wrong tool chosenOverlapping descriptions — make each tool’s purpose distinct
Action errors outMissing/typed-wrong inputs — check the trace’s arguments
Works for you, not othersPermissions or auth — “test as another user”
Connector missingBlocked by environment DLP policy

Debug method: open the trace, find the first turn that diverges, fix that one thing, re-test.

Conversation Design

Handle the Unhappy Path

  • Write a real fallback — not “I didn’t understand”
  • Offer next steps or a human hand-off
  • Confirm before destructive or costly actions
  • Echo back collected values before submitting

Keep Turns Tight

  • One question at a time when slot-filling matters
  • Short answers; link out for the long version
  • Use the user’s name and context from system vars
  • Set expectations: “this takes ~30 seconds”

Good agents feel designed, not generated — the unhappy path is where that shows.

Teams and M365 channels usually require an admin approval step — plan for it.

Analytics & Iteration

Engagement

Sessions, active users, channels — is anyone using it?

Resolution Rate

Resolved vs. escalated vs. abandoned — the headline metric.

Topic / Tool Usage

What gets used, what never fires, what fails often.

Transcripts

Read real conversations — the richest source of fixes.

Ship small, read transcripts, fix the top failure, repeat. That loop beats big upfront design.

From Dev to Prod (ALM)

Package It

  • Put the agent in a solution (zip of artifacts)
  • Export the YAML to git — review changes in PRs
  • Don’t hand-edit directly in the prod maker portal

Promote It

  • Pipelines move the solution Dev → Test → Prod
  • Connection references rebind per environment
  • Each environment keeps its own DLP and caps

Same ALM model as the rest of Power Platform — environments, solutions, pipelines.

Maker Best Practices

1Start with one topic and one knowledge source; expand on usage signal.
2Write every tool and source description like a prompt — the router reads them.
3Iterate instructions in the test pane, one change at a time.
4Always design the unhappy path and a human hand-off.
5Confirm before any destructive or costly action.
6Test as another user to catch permission and auth gaps.
7Read the trace, not the chat bubble, when something breaks.
8Version via solutions + git; promote through pipelines, never edit prod live.
