What is Sentry?

  • An application monitoring platform that tells you when your code breaks — and gives you the context to fix it fast
  • One product spanning error & exception tracking, performance tracing, session replay, profiling, logs, and uptime/cron monitoring
  • A lightweight SDK runs inside your app, captures events, and sends them to Sentry, where they are grouped into actionable issues
  • Built developer-first: full stack traces, the exact line of code, request data, breadcrumbs, and the release that introduced the bug
  • Open source core (getsentry/sentry) — run the managed SaaS at sentry.io or self-host it yourself
# The whole idea in one call — Sentry captures, groups, and alerts
try:
    process_payment(order)
except Exception as err:
    sentry_sdk.capture_exception(err)   # full traceback + context, sent to Sentry
    raise

SDK & DSN

The SDK captures events; the DSN (Data Source Name) is the URL that tells it which project to send to. The DSN is public-safe — it can only write events.

Events

A single error, transaction, or message. Events carry a stack trace, tags, breadcrumbs, user, and release. Similar events are grouped into one issue.

Projects

One per application or service (frontend, API, worker). Each project has its own DSN, issues, alerts, and settings.

Orgs & Environments

An organization contains teams and projects. Environments (production, staging) tag events so you can filter by where they happened.

Quickstart — Install & Init

npm install @sentry/browser     # or @sentry/react, @sentry/nextjs
npm install @sentry/node        # backend
      
// Browser / frontend — initialize as early as possible
import * as Sentry from '@sentry/browser';

Sentry.init({
  dsn: 'https://examplePublicKey@o0.ingest.sentry.io/0',
  environment: 'production',
  release: 'my-app@1.4.2',
  tracesSampleRate: 0.2,          // 20% of transactions for performance
});
      
// Node.js — instrument.js, imported before everything else
const Sentry = require('@sentry/node');

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  tracesSampleRate: 0.2,
});
// Errors are now captured automatically; verify with a test throw

Error & Exception Monitoring

Once initialized, the SDK hooks global handlers and captures unhandled exceptions and rejections automatically. You can also capture explicitly.

import * as Sentry from '@sentry/browser';

// 1. Capture a caught exception — keeps the full stack trace
try {
  riskyOperation();
} catch (err) {
  Sentry.captureException(err);
}

// 2. Capture a message with a severity level
Sentry.captureMessage('Payment retried 3 times', 'warning');

// 3. Wrap a block and grab the returned event ID (e.g. to show the user)
const eventId = Sentry.captureException(new Error('Checkout failed'));

Framework SDKs add automatic capture: React Error Boundaries, Express/Next.js error middleware, and unhandled promise rejections — no manual try/catch needed for the common cases.

Issues & Grouping

How grouping works

  • Sentry computes a fingerprint from the stack trace + exception type
  • Matching events roll up into one issue — not 10,000 duplicates
  • Override with a custom fingerprint when defaults are too broad or too narrow

Issue lifecycle

  • States: Unresolved → Resolved → Ignored/Archived
  • Assign to a teammate; sync to Jira/GitHub
  • Regression detection reopens an issue if it recurs after being resolved
// Force two distinct error messages into the same issue
Sentry.captureException(err, {
  fingerprint: ['database', 'connection-timeout'],
});

Resolve an issue and Sentry watches future releases — if it shows up again it is flagged as a regression and reopened automatically.

Context & Enrichment

Raw stack traces are good; enriched ones are great. Attach who, where, and what so you can reproduce the bug.

import * as Sentry from '@sentry/browser';

// Identify the affected user (drives "users impacted" counts)
Sentry.setUser({ id: '42', email: 'jane@acme.com', username: 'jane' });

// Tags are indexed & searchable/filterable in the UI
Sentry.setTag('payment.provider', 'stripe');

// Context is structured extra data shown on the event
Sentry.setContext('order', { id: 'ord_991', total: 149.0, currency: 'USD' });
      
// Scope a tag to a single event without polluting global state
Sentry.withScope((scope) => {
  scope.setTag('feature', 'checkout-v2');
  scope.setLevel('fatal');
  Sentry.captureException(err);
});

Tags are searchable and aggregable; context is detailed but not indexed; scopes control how long enrichment lives.

Breadcrumbs

Breadcrumbs are a trail of events leading up to an error — the “what happened just before the crash” timeline attached to every issue.

Captured automatically

  • Console logs & network (XHR/fetch) requests
  • UI clicks and navigation/route changes
  • DB queries and HTTP calls on the backend

Add your own

Sentry.addBreadcrumb({
  category: 'auth',
  message: 'User completed 2FA',
  level: 'info',
  data: { method: 'totp' },
});

When an error fires, the last ~100 breadcrumbs ship with it — so you see the click, the failed API call, and the exception as one story. Control volume with maxBreadcrumbs and the beforeBreadcrumb hook.

Releases & Deploy Tracking

  • Tag every event with a release (a version string, often the git SHA) so each error is tied to the exact build that shipped it
  • Suspect commits: Sentry links an issue to the commit — and the author — that most likely introduced it
  • Release health: crash-free sessions/users, adoption, and regressions per release
  • Mark deploys so you can correlate a spike in errors with the moment a version went live
# Create the release, associate commits, and finalize — via sentry-cli
export SENTRY_RELEASE="my-app@$(git rev-parse --short HEAD)"

sentry-cli releases new "$SENTRY_RELEASE"
sentry-cli releases set-commits "$SENTRY_RELEASE" --auto
sentry-cli releases finalize "$SENTRY_RELEASE"
sentry-cli releases deploys "$SENTRY_RELEASE" new -e production

Pass the same value to Sentry.init({ release }) so the SDK and CLI agree — that link powers source maps, suspect commits, and regression tracking.

Source Maps

Minified production JS produces unreadable stack traces. Upload source maps so Sentry un-minifies them back to your original code, with the exact line and column.

// next.config.js / vite.config — bundler plugins automate upload at build time
import { sentryVitePlugin } from '@sentry/vite-plugin';

export default {
  build: { sourcemap: true },        // emit source maps
  plugins: [
    sentryVitePlugin({
      org: 'my-org',
      project: 'my-app',
      authToken: process.env.SENTRY_AUTH_TOKEN,
    }),
  ],
};
      
# Or upload manually with the CLI, keyed to the same release
sentry-cli sourcemaps inject ./dist
sentry-cli sourcemaps upload ./dist --release "$SENTRY_RELEASE"

Modern SDKs use Debug IDs to match maps to bundles reliably. Plugins exist for Webpack, Vite, Rollup, esbuild, and the Next.js/Remix SDKs do it for you.

Performance Monitoring & Tracing

Sentry tracing captures transactions (a unit of work like a page load or request) made of nested spans (DB query, HTTP call, render).

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  tracesSampleRate: 0.2,            // sample 20% of transactions
  // or sample dynamically:
  tracesSampler: (ctx) => (ctx.name.includes('/checkout') ? 1.0 : 0.1),
});
      
// Create a custom span around a slow operation
Sentry.startSpan(
  { name: 'generate-report', op: 'task' },
  async () => {
    await buildPdf();              // timed automatically
  },
);

Most spans are auto-instrumented — HTTP clients, database drivers, render frameworks — so you get a waterfall view of where time goes with minimal code.

// Wire frontend & backend together via tracePropagationTargets
Sentry.init({
  tracePropagationTargets: ['localhost', /^https:\/\/api\.myapp\.com/],
});
// Outgoing fetch/XHR to those targets carry the trace headers automatically

Span Metrics & Insights

From trace spans Sentry derives Insights — ready-made views that surface concrete performance problems without you building dashboards.

Web Vitals

Core Web Vitals (LCP, CLS, INP, FCP, TTFB) per page, with scores and the spans behind a poor measurement.

Slow DB Queries

Aggregated query performance: which statements are slowest, called most, and trending worse over time.

N+1 Detection

Performance issues auto-detect N+1 queries, render-blocking assets, and consecutive HTTP calls.

Resources & HTTP

Outbound API and asset timings — spot a third-party dependency dragging down your p95.

These appear as Performance Issues alongside errors — same triage, assignment, and alerting workflow.

Session Replay

Session Replay reconstructs a video-like DOM playback of what the user did — clicks, scrolls, network, and console — right up to the error.

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  integrations: [Sentry.replayIntegration({
    maskAllText: true,         // privacy: mask text by default
    blockAllMedia: true,       // don't record images/video
  })],
  replaysSessionSampleRate: 0.1,    // 10% of all sessions
  replaysOnErrorSampleRate: 1.0,    // 100% of sessions that hit an error
});
  • Replays are tied to issues — jump from an error straight to the recording
  • Privacy-first: text and inputs are masked by default; add .sentry-mask / .sentry-unmask classes for fine control
  • Sample cheaply for all sessions, but capture every errored session

Profiling

Profiling samples your code's call stack to show exactly which functions burn CPU — the function-level detail under a slow span.

import * as Sentry from '@sentry/node';
import { nodeProfilingIntegration } from '@sentry/profiling-node';

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  tracesSampleRate: 1.0,
  integrations: [nodeProfilingIntegration()],
  profileSessionSampleRate: 1.0,    // continuous profiling
  profileLifecycle: 'trace',        // profile while traces run
});

Flame Graphs

Visualize the call tree; wide frames are where time is spent. Drill into the hottest path.

Continuous vs Transaction

Profile always-on (continuous) or only while a transaction runs — available for Python, Node, Go, mobile, and more.

Logs

Sentry Logs brings structured logging into the same platform — so logs sit next to the errors and traces they relate to, not in a separate tool.

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  enableLogs: true,                 // turn on log capture
});

const { logger } = Sentry;

// Structured logs with template attributes
logger.info('User %s checked out cart %s', [userId, cartId], {
  total: 149.0,
  itemCount: 3,
});
logger.error('Payment gateway timeout', { provider: 'stripe', attempt: 3 });
  • Logs are correlated with traces — filter to the logs emitted during one request
  • Search and filter by attributes; build alerts on log volume or patterns
  • SDK integrations can also forward existing console / logging-framework output

Alerts & Notifications

Issue Alerts

  • Fire when a new issue appears, regresses, or crosses a frequency threshold
  • Conditions + filters (level, environment, tag) and actions
  • Great for “tell me when something breaks”

Metric Alerts

  • Threshold on a metric over time: error rate, p95 latency, crash-free rate, failure rate, throughput
  • Static or anomaly-based thresholds
  • Great for “tell me when the trend is bad”

Route notifications to Slack, PagerDuty, Microsoft Teams, Discord, email, or any webhook. Use ownership rules to auto-route issues by code path to the right team.

Alert hygiene matters: too many alerts and people tune them out — alert on what is actionable.

Dashboards & Discover

  • Discover lets you query across events — errors, transactions, and spans — with a flexible search syntax and aggregations
  • Custom dashboards assemble widgets (charts, tables, big numbers) from those queries for an at-a-glance health view
  • Slice by any tag: by release, environment, browser, endpoint, customer — whatever you set
  • Save and share views; widgets can drive team-level overviews
# Sentry search query syntax — used in Discover, dashboards, and issue search
is:unresolved environment:production release:my-app@1.4.2

# Aggregate: 95th percentile transaction duration for the checkout route
transaction:/checkout  p95(transaction.duration):>2s

# Errors affecting a specific customer, last 24h
user.email:jane@acme.com  level:error

The same query language powers issue search, alerts, and dashboard widgets — learn it once.

Cron & Uptime Monitoring

Cron Monitors

Scheduled jobs send check-ins. Sentry alerts if a job is missed, runs too long, or fails — catching silent batch failures.

const id = Sentry.captureCheckIn({
  monitorSlug: 'nightly-billing',
  status: 'in_progress',
});
// ... run the job ...
Sentry.captureCheckIn({
  monitorSlug: 'nightly-billing',
  checkInId: id, status: 'ok',     // or 'error'
});

Uptime Monitors

Sentry periodically requests a URL from multiple regions and alerts on downtime, errors, or slow responses.

  • Configurable interval & expected status
  • Downtime creates an issue you can route & assign
  • Pairs with error/perf data for full-stack visibility

Define a cron monitor's schedule (crontab or interval) and grace period so a slightly-late job is not a false alarm.

Data Management & Security

Privacy & PII

  • Data scrubbing strips passwords, tokens, and credit cards server-side
  • sendDefaultPii: false keeps PII out at the source
  • beforeSend hook to redact or drop events client-side
  • Replay masking; advanced server-side scrubbing rules

Volume & Governance

  • Sampling & rate limiting control event volume and cost
  • Inbound filters drop noise (browser extensions, bots)
  • Quotas & spike protection; configurable retention
  • SSO/SAML, audit logs, fine-grained roles
Sentry.init({
  dsn: process.env.SENTRY_DSN,
  sendDefaultPii: false,
  beforeSend(event) {
    if (event.request?.headers) delete event.request.headers['Authorization'];
    return event;                  // return null to drop the event entirely
  },
});

Sentry is SOC 2 Type II certified and supports GDPR/CCPA workflows, with EU and US data-residency options.

Best Practices

1 Initialize the SDK as early as possible — before app code runs — so nothing escapes capture
2 Set a release and upload source maps every deploy — readable traces and suspect commits
3 Tag the environment so you can separate production from staging noise
4 Tune tracesSampleRate for cost vs visibility; sample high-value routes more
5 Enrich events with user, tags, and context so issues are reproducible
6 Scrub PII with beforeSend and keep sendDefaultPii off by default
7 Use inbound filters & ignoreErrors to silence known noise (extensions, bots)
8 Practice alert hygiene — alert only on actionable issues, route by ownership
9 Triage regularly: resolve, assign, and link issues to your tracker
10 Capture replays on error (low session rate, 100% on error) for cheap, high-signal debugging
