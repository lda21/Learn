Turborepo

High-performance build system for JavaScript/TypeScript monorepos

Monorepo Caching CI Workspaces

Why Turborepo?

The pain

  • Many packages, repeated build/test/lint
  • CI rebuilds everything on every PR
  • Unclear task graph between apps & libs
  • Slow local feedback loops

The bet

  • Declare a task graph once
  • Cache task outputs locally & remotely
  • Schedule work with max parallelism
  • Stay compatible with npm/pnpm/yarn workspaces

Mental model

Workspaces
packages/*
→
turbo.json
tasks + deps
→
Scheduler
parallel + cache
→
Artifacts
dist, coverage…

Turborepo does not replace your package manager. It orchestrates scripts that already exist in each package’s package.json.

Workspace layout

apps/
  web/          # Next.js app
  docs/         # docs site
packages/
  ui/           # shared components
  config-eslint/
  tsconfig/
package.json    # workspaces root
turbo.json      # task pipeline
pnpm-workspace.yaml

Root owns workspaces + Turbo. Packages own their scripts and outputs.

Root package.json scripts

{
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev --parallel",
    "lint": "turbo run lint",
    "test": "turbo run test",
    "format": "prettier -w \"**/*.{ts,tsx,md}\""
  },
  "devDependencies": {
    "turbo": "^2"
  }
}

Developers run pnpm build at the root; Turbo fans out to each package that defines build.

turbo.json — tasks

{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "lint": {},
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}

dependsOn & ^

dependsOn: ["build"]

Same package must finish its own build first.

dependsOn: ["^build"]

Upstream workspace dependencies must build first (the caret = topological deps).

Rule of thumb: libraries publish/build before apps that import them.

Cache inputs & outputs

Hash inputs

Source files, env vars you declare, dependency hashes, task config.

Outputs

Declare precisely (dist/**). Missed outputs = broken cache restores.

Hit

Skip work; restore artifacts. Log shows FULL TURBO.

Miss

Run script; write new cache entry for next run / teammate / CI.

Local cache

  • Default cache lives under node_modules/.cache/turbo (or configured cache dir).
  • Same machine + same inputs ⇒ instant replay.
  • Great for toggling branches and re-running lint/test.
  • Not shared across laptops or CI runners — that’s remote cache.
pnpm exec turbo run build --force   # bypass cache
pnpm exec turbo run build --dry     # show plan

Remote cache

Why

  • CI starts cold every time
  • Share hits across PRs & teammates
  • Biggest wall-clock win in large repos

How (Vercel Remote Cache)

npx turbo login
npx turbo link
# or set TURBO_TOKEN + TURBO_TEAM in CI

Self-hosted / S3-compatible caches exist; out of scope for this course.

Filters

turbo run build --filter=web
turbo run test --filter=./packages/ui
turbo run lint --filter=...@acme/ui
turbo run build --filter=web...   # web + dependencies
turbo run build --filter=...web   # web + dependents
turbo run build --filter=!./apps/docs

Filters keep CI focused: changed packages + their dependents, not the entire monorepo.

CI pattern

# GitHub Actions sketch
- uses: actions/checkout@v4
  with: { fetch-depth: 0 }
- run: pnpm install
- run: pnpm exec turbo run lint test build
      --filter=...[origin/main]
  env:
    TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
    TURBO_TEAM: ${{ vars.TURBO_TEAM }}

--filter=...[origin/main] builds packages changed since main and their dependents.

Environment variables

Affect the hash

Declare under env / passThroughEnv / global env in turbo.json when values change outputs (e.g. NEXT_PUBLIC_*).

Silent bugs

Forgot to list an env var ⇒ cache hit with the wrong build. Treat env as part of the contract.

Turborepo vs Nx

Turborepo

  • Thin layer over existing workspaces
  • Fast to adopt
  • Cache + task graph focus
  • Less codegen / project graph UI

Nx

  • Richer project graph & plugins
  • Generators, module boundaries
  • Steeper setup / conventions
  • Great when you want a platform

Pick Turbo when you want speed with minimal ceremony; Nx when you want opinionated workspace tooling.

Common pitfalls

1. Missing outputs

Cache “hits” but dist/ empty in CI → declare outputs correctly.

2. Non-deterministic tasks

Timestamps / random IDs in build output poison the cache.

3. Caching dev

Keep dev with cache: false + persistent: true.

4. Ignoring ^build

Apps compile against stale lib sources → flaky types.

Practical checklist

  • Workspaces compile in isolation with clear package boundaries
  • Every cacheable task lists accurate outputs
  • ^build wired for anything that imports workspace packages
  • Remote cache token present in CI
  • Filtered pipelines on PRs; full pipeline on main
  • --dry reviewed when onboarding a new package
