What is Metabase?

  • An open-source business intelligence tool that lets anyone ask questions about data and share the answers
  • Built for self-service analytics — non-technical users explore data through a point-and-click interface, no SQL required
  • Connects directly to your existing databases and data warehouses — it queries them live, it is not a data store
  • Power users still get a full native SQL editor with variables, parameters, and snippets
  • Available as Metabase Cloud (hosted SaaS) or self-hosted (free open-source edition, plus paid Pro/Enterprise tiers)

The core loop: ask a question → visualize it → save it → pin it to a dashboard → share or schedule it.

The Application

A single JVM web app. It builds queries, renders charts, and manages users — but does not store your business data.

Application Database

A separate metadata DB (use Postgres in production; the default H2 is for trials only) holds questions, dashboards, users, and settings.

Connected Data Sources

Your warehouses and databases. Metabase queries them live; results are rendered (and optionally cached), never copied wholesale.

How to Run It

Metabase Cloud, a Docker container, or the runnable metabase.jar. Cloud is the simplest; Docker is the common self-host path.

Connecting Databases

Add a data source in Admin → Databases with host, port, credentials, and driver. Metabase ships drivers for many engines, with more as community plugins.

Common Sources

  • PostgreSQL, MySQL / MariaDB
  • BigQuery, Snowflake, Redshift
  • SQL Server, Oracle, ClickHouse
  • Databricks, Athena, SQLite

Sync & Scan

  • Sync reads the schema — tables, columns, types
  • Scan samples field values to power filters & types
  • Both run on a schedule you control
  • Use a read-only DB user for safety

Tip: grant only SELECT on the schemas you want exposed, and prefer a dedicated reporting replica so analytics never strains production.

The Data Model & Metadata

In Admin → Table Metadata you curate how raw tables appear to users — good metadata is what makes self-service actually work.

Semantic Types

Tag fields beyond their raw type: Currency, Category, Email, Latitude. This drives formatting, filters, and chart choices.

Friendly Names & Descriptions

Rename cust_id to "Customer ID" and add descriptions, so business users understand each column.

Foreign Keys

Declare FK relationships so the query builder can join and drill across tables automatically.

Hidden Tables

Hide noisy staging or internal tables from the query builder to keep the data picker clean.

Segments are saved, reusable filter definitions (e.g. "Active Customers") that appear as one-click options across questions.

Questions: The Building Block

A question is a single query and its visualization. Everything in Metabase — dashboards, alerts, models — is built from questions. There are three ways to create one:

  • Query Builder — the visual "notebook" editor for point-and-click queries
  • Native query — raw SQL (or the database's native language) for full power
  • Saved questions & models — reuse an existing query as the starting data for a new one

Save a question into a collection, then pin it to dashboards or wire alerts to it.

The Query Builder (Notebook)

The notebook editor builds queries as a stack of steps — it compiles down to SQL for you, so no SQL knowledge is needed.

Core Steps

  • Filter — narrow rows by conditions
  • Summarize — aggregate: count, sum, average…
  • Group by — break out by a dimension
  • Join — combine tables (uses FKs)
  • Sort & Row limit

Custom Columns

Add computed columns with an Excel-like expression language:

[Total] - [Discount]

case([Plan] = "pro", "Paid", "Free")

datetimeDiff([Signup], [Churn], "day")

Click "View the SQL" on any notebook question to see (and learn from) the generated query.

Native SQL Questions

When the query builder isn't enough — window functions, CTEs, complex joins — drop into the native SQL editor and write the database's own language directly.

-- Monthly revenue with a running total
SELECT
  date_trunc('month', o.created_at) AS month,
  sum(o.total)                      AS revenue,
  sum(sum(o.total)) OVER (
    ORDER BY date_trunc('month', o.created_at)
  )                                 AS running_total
FROM orders o
WHERE o.status = 'paid'
GROUP BY 1
ORDER BY 1;
  • Results can be visualized just like notebook questions
  • Save SQL snippets to reuse common clauses across queries
  • A native question can be turned into a model so others build on it without seeing the SQL

SQL Variables & Parameters

Make SQL questions interactive with variables in double braces. They render as filter widgets above the query.

SELECT *
FROM orders
WHERE status = {{order_status}}        -- text / number / date variable
  [[ AND created_at > {{start_date}} ]]  -- optional clause: only applied if set

Variable Types

  • Text / Number / Date — simple inputs
  • Field Filter — maps to a column; gives smart widgets (dropdowns, date ranges) and powers dashboard filters

Optional Clauses

Wrap a clause in [[ … ]] and it is included only when its variable has a value — perfect for optional filters.

Field filters are the bridge: they let dashboard filters drive your native SQL questions.

Visualizations

Any question can be rendered as many chart types — Metabase suggests sensible defaults based on your data and semantic types.

Comparisons

Bar, row, and combo charts to compare categories or stack series.

Trends Over Time

Line and area charts, plus the single-number Trend with period-over-period deltas.

Composition & Flow

Pie / donut, funnel, and pivot tables for cross-tab breakdowns.

Geospatial & Single Value

Region and pin maps, gauges, progress bars, and big-number scalars for KPIs.

Pick the right one: time → line, categories → bar, one KPI → number/trend, part-of-whole → pie (sparingly), location → map.

Models

A model is a curated, reusable dataset that acts as a clean starting point — the closest Metabase comes to a lightweight modeling layer.

What Models Do

  • Wrap a notebook or SQL query as a named, reusable table
  • Join, rename, and clean fields once, centrally
  • Let users build new questions on top without touching raw tables
  • Carry their own metadata (types, descriptions, FKs)

Why Use Them

  • Hide messy schemas behind business-friendly datasets
  • Encode business logic in one place
  • Surface curated data in the data picker, separate from raw tables
  • Can be persisted for speed (see caching)

Treat models as your semantic foundation: define "Orders", "Customers", "Active Subscriptions" once, and have everyone analyze from there.

Dashboards

A dashboard arranges saved questions (cards) on a grid to tell a story or monitor a process at a glance.

Cards & Layout

Drag-and-drop questions onto a responsive grid; resize and arrange them into a coherent view.

Tabs

Split a large dashboard into tabs (e.g. Overview, Revenue, Retention) to organize many cards.

Text & Headings

Add markdown text cards and section headings to give context and structure.

Auto-refresh & Full-screen

Set refresh intervals and present in full-screen — great for TV/wallboard displays.

Cards stay live: editing the underlying question updates it everywhere it is pinned.

Filters & Drill-Through

  • Dashboard filters — add a filter widget (date, category, ID) and map it to many cards at once, so one control updates the whole page
  • Filters connect to query-builder columns directly, or to native SQL via field filter variables
  • Linked filters — chain filters so one narrows the options of another (e.g. State → City)
  • Drill-through — click any data point to zoom in, break out by another dimension, or jump to the underlying rows
  • Click behavior — configure a card so clicking navigates to another dashboard, question, or external URL, passing filter values along

Metrics & the Semantic Layer

Metrics are official, reusable definitions of a business measurement — defined once so everyone reports the same number.

What a Metric Is

  • A named aggregation built on a model or table
  • e.g. "Net Revenue" = sum of paid order totals minus refunds
  • Reusable in the query builder and on dashboards
  • One source of truth — no more conflicting "revenue" numbers

Semantic Layer

  • Models define the curated tables
  • Metrics define the trusted measures
  • Together they form a lightweight semantic layer
  • Governs definitions so self-service stays consistent

Encoding key measures as metrics is what keeps a fast self-service culture from drifting into "every dashboard has its own definition of revenue."

Alerts & Subscriptions

Push results to people instead of making them check — via email or Slack.

Dashboard Subscriptions

  • Schedule a dashboard to send on a cadence (daily, weekly…)
  • Delivered as email or to a Slack channel
  • Can apply specific filter values per subscription
  • Great for recurring exec / team reports

Alerts

  • Attached to a single question
  • When results exist — fire when a query returns rows
  • Goal line — fire when a metric crosses a threshold
  • Send once, or every time the condition holds

Configure email (SMTP) and Slack once in Admin, and any user can wire up their own alerts and subscriptions.

Collections, Permissions & Sandboxing

Collections

Folders that organize questions, dashboards, and models. Nest them by team or topic; permissions are set per collection.

Groups

Users belong to groups; permissions are granted to groups, not individuals. Two built-ins: Administrators and All Users.

Data & Collection Permissions

Data permissions control which databases/tables a group can query; collection permissions control view/curate access to saved content.

Data Sandboxing (Pro)

Row- and column-level security: filter a table so each user sees only their own rows (e.g. by customer_id) — key for multi-tenant access.

Sandboxing and granular data permissions are paid (Pro/Enterprise) features; collections and group permissions exist in the free edition.

Embedding Analytics

Surface Metabase content inside your own app. Three approaches, increasing in power:

Static Embedding

Sign a question or dashboard with a JWT and drop it in an iframe. Locked parameters; read-only. Available in the free edition.

Interactive Embedding

Embed the full app with drill-through and self-service, with SSO + your permissions/sandboxing applied. A Pro/Enterprise feature.

Embedded SDK for React

Embed individual components into a React app for deep, native-feeling customer-facing analytics (Pro/Enterprise).

White-Labeling

Customize colors, logos, and fonts so embedded analytics match your product's brand.

# Signed static embed: server mints a JWT, browser loads the iframe
<iframe src="https://mb.example.com/embed/dashboard/JWT_TOKEN#bordered=true"></iframe>

Caching & Performance

Because Metabase queries your live database, performance comes from caching and smart scoping.

Query Caching

  • Cache query results so repeated loads don't re-hit the DB
  • Set policies globally, per-database, or per-question
  • Invalidate on a schedule or after a duration

Model Persistence

  • Materialize models into physical tables in your warehouse
  • Queries built on the model read the fast table
  • Refreshed on a schedule you set
  • Scale the app with adequate JVM memory and a Postgres app DB; run multiple instances behind a load balancer for HA
  • Avoid huge unfiltered scans — add default filters, row limits, and push heavy transforms into the warehouse

X-rays & Automated Insights

X-rays auto-generate an exploratory dashboard from any table, column, segment, or single value — instant insight with zero setup.

  • Click "X-ray this" on a table to get distributions, trends, and breakdowns in seconds
  • X-ray a single record or value to see related context and comparisons
  • New databases get auto-generated starter dashboards so there's something useful from day one
  • Use X-rays as a jumping-off point — "Save this" turns an exploration into real questions and dashboards you can refine

API & Tooling

Metabase is automatable — the same actions the UI takes are exposed over a REST API, and content can be version-controlled.

# Authenticate, then list all dashboards
SESSION=$(curl -s -X POST https://mb.example.com/api/session \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin@example.com","password":"secret"}' | jq -r .id)

curl -s https://mb.example.com/api/dashboard \
  -H "X-Metabase-Session: $SESSION"
  • REST API — manage questions, dashboards, users, permissions, and run queries programmatically
  • Serialization (export/import) dumps content to YAML so you can put dashboards under version control and promote dev → prod
  • Wire serialization into CI/CD to review and deploy analytics content like code (Pro/Enterprise for the full workflow)

Best Practices

1 Connect with a read-only user on a reporting replica — never let BI strain production
2 Invest in table metadata: friendly names, descriptions, semantic types, and foreign keys
3 Build models for curated, business-friendly datasets instead of exposing raw tables
4 Define shared metrics so everyone reports the same numbers
5 Use clear, consistent naming and organize content into team collections
6 Grant permissions to groups, not individuals; use sandboxing for row-level access
7 Add caching and persist models for slow or popular queries
8 Avoid huge unfiltered queries — add default filters and row limits
9 Use Postgres for the app DB in production — never ship on the default H2
10 Version content with serialization and promote changes through environments
