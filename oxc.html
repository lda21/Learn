Oxc Fundamentals

The Rust-based JS/TS compiler toolkit — parser, linter, transformer, minifier

Oxc Oxlint Toolchain JavaScript

The toolchain tax

Today's stack

  • ESLint walks a JS AST, plugin by plugin
  • Babel / SWC / tsc each re-parse for transforms
  • Terser or esbuild minify yet another tree
  • Prettier or Biome format from a fourth parse

What that costs

  • CI minutes grow with every rule and package
  • Behavior drifts between tools that never share an AST
  • Monorepos wait on a single-threaded JS linter
  • Toolchain teams maintain four parsers, four bugs

Oxc's bet: one Rust compiler foundation, many tools, one parse.

What Oxc is

Oxc (pronounced /oʊ ɛks siː/) is the Oxidation Compiler — a suite of high-performance JavaScript and TypeScript tools written in Rust. Oxidation is the chemical process that creates rust.

A suite, not a single binary

End-user tools (Oxlint, Oxfmt) plus reusable compiler crates you can embed.

VoidZero's toolchain

Oxc powers Rolldown, Vite 8's bundler, so transform and minify already ship in production builds.

Performance is a feature

Speed is a product requirement. Performance regressions are treated as bugs.

Compatibility on purpose

When Oxc differs from ESLint, Babel, or TypeScript, the difference should be documented — not accidental.

One parse, many tools

Core crates

oxc_parser

JS/TS/JSX parser. npm: oxc-parser. Production-grade; Test262 stage 4.

oxc_linter

ESLint-compatible engine. The oxlint CLI is the app on top.

oxc_transformer

TS strip, JSX, syntax lowering, isolated .d.ts. npm: oxc-transform.

oxc_minifier

Dead-code, mangling, whitespace. npm: oxc-minify. Default in Rolldown.

The umbrella crate oxc re-exports them. Tool authors also reach for oxc_resolver and oxc_codegen; this course stays on the four the Brief names.

Parser

What you get

  • ~3× SWC parser, ~5× Biome on published benches
  • ESTree for JS/JSX; TS-ESTree for TypeScript
  • ESM metadata without a second walk
  • Fast mode skips semantic errors (default)

Node API

import { parseSync } from "oxc-parser";

const { program, errors, module } =
  parseSync("app.tsx", source);

// language from the filename
// or set lang: "tsx"

Use showSemanticErrors: true when you need duplicate-binding checks. Leave fast mode on inside a bundler that already type-checks elsewhere.

Minifier

What it does

  • Dead-code elimination
  • Syntax shortening + whitespace drop
  • Name mangling (and selected properties)
  • Fixed-point passes until nothing shrinks

How you consume it

import { minifySync } from "oxc-minify";

const { code } = minifySync(
  "app.js",
  source
);

Rolldown uses oxc-minify by default — no extra install in a Vite 8 / Rolldown app.

It assumes the input is already semantically valid and parses in fast mode. Do not treat minify as your type-check or lint step.

Oxlint is the product most teams touch

Why it exists

A dedicated JS/TS linter on the Oxc stack. Convention over config: correctness rules are on by default, no plugin install for the common set.

Coverage

865+ built-in rules spanning ESLint core, TypeScript (including type-aware), React, Jest, Vitest, import, Unicorn, jsx-a11y, Next.js.

1 Native Rust plugins — no giant JS dep tree
2 Automatic fixes via --fix
3 Framework files: lints <script> in Vue / Svelte / Astro
4 JS plugins exist but are alpha

CLI basics

Install and scripts

pnpm add -D oxlint

# package.json
"lint": "oxlint",
"lint:fix": "oxlint --fix"

Everyday flags

npx oxlint@latest
oxlint --init
oxlint -c .oxlintrc.json
oxlint --type-aware
oxlint -D correctness -W suspicious
oxlint -D no-alert -A no-plusplus

-A allow, -W warn, -D deny. Flags apply left to right and override the config file. Zero config is valid: npx oxlint already runs correctness checks.

Configuration

{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "categories": { "correctness": "error", "suspicious": "warn" },
  "rules": {
    "no-console": "error",
    "eslint/prefer-const": ["error", { "destructuring": "any" }]
  },
  "overrides": [
    { "files": ["scripts/*.js"], "rules": { "no-console": "off" } }
  ]
}

Auto-discovers .oxlintrc.json / .oxlintrc.jsonc / oxlint.config.ts. JSON aims at ESLint v8 eslintrc shape. One config file per directory. oxlint.config.ts needs the Node package, not a standalone binary.

Categories, plugins, ignores

Categories

  • correctness — default on
  • suspicious / pedantic
  • perf, style, restriction
  • nursery — unstable, may change

Plugins & ignores

  • plugins: ["unicorn","typescript"] replaces the default set
  • Respects .gitignore and leftover .eslintignore
  • Prefer ignorePatterns in the Oxlint config
  • Inline comments work; migrate them with @oxlint/migrate

Type-aware and multi-file

Type-aware lint

Oxlint uses tsgo (the Go port of TypeScript, a.k.a. TypeScript 7) so floating-promise and similar rules see real TS types.

oxlint --type-aware
# or options.typeAware: true

options.typeCheck is still experimental. Install oxlint-tsgolint when the docs for your oxlint version require it.

Multi-file analysis

Builds a project-wide module graph and shares parse/resolve across rules. This is how import-cycle checks stay cheap instead of becoming ESLint's classic CI cliff.

Biome's type-aware path uses its own inference and still lists coverage as improving — different trade-off, not a drop-in.

Migrate from ESLint

npx @oxlint/migrate
# optional path to eslint.config.js / .mjs
1 Reads ESLint flat config (v9/v10)
2 Writes .oxlintrc.json with severities + overrides
3 Maps globals to Oxlint env / globals
4 Keeps root ignores; --details lists leftovers

Legacy .eslintrc.* is not auto-migrated. Convert to flat with @eslint/migrate-config first, or translate simple eslintrc by hand — the JSON shape is close. Pin oxlint and @oxlint/migrate to the same version.

Two adoption paths

Replace (most repos)

  • Run @oxlint/migrate
  • Swap CI from eslint to oxlint
  • Keep Prettier or trial Oxfmt separately
  • Drop unused ESLint plugins from package.json

Incremental (large / plugin-heavy)

  • Oxlint first in CI for the fast pass
  • eslint-plugin-oxlint turns off overlapping ESLint rules
  • ESLint keeps the remaining JS plugins
  • Shrink the ESLint set as native coverage grows

Stay on ESLint alone only when you depend on unsupported edge-case plugin behavior. JS plugins in Oxlint are alpha and not semver-guaranteed.

Why it is fast

Rust + arena alloc

oxc_allocator bumps memory for the AST. Parse once; later passes walk the same tree.

Parallel file walk

Oxlint fans out across cores. Project benches: ~50–100× ESLint, seconds on large monorepos.

Native rules

Common plugins are Rust, not a JS visitor per rule. No @typescript-eslint parser tax.

Shared resolve

Multi-file analysis reuses the module graph. Import rules do not re-parse the repo per rule.

Direct oxlint users

Public adopters include Preact, Shopify, ByteDance, and Shopee. Resolver users include knip and swc-node.

Pitfalls for toolchain engineers

1 plugins is a replace, not a merge — list the full set
2 TypeScript config files need Node that can run TS (22.18+ / 24+)
3 Standalone oxlint binary: use .oxlintrc.json, not oxlint.config.ts
4 Reserved plugin names (react, import, …) collide with JS plugins
5 Minify assumptions: semantically valid input, fast parse
6 Nursery rules and JS plugins will move under you
7 Type-aware lint ≠ tsc --noEmit; keep a typecheck job
8 Do not deep-custom the AST until you own the crate versions
