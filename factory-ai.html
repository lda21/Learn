Why Factory.ai?

The Problem

  • Engineers spend hours on routine work: refactors, bug triage, doc lookups
  • Single-purpose AI tools don't span the full SDLC
  • Context lives scattered across GitHub, Jira, Slack, PagerDuty
  • Generalist agents lack role boundaries and accountability

The Factory Approach

  • Droids — specialized autonomous agents per role
  • Missions — long-running, multi-step delegated work
  • Everywhere — IDE, CLI, Desktop, Slack, web
  • Enterprise — security, audit, org-wide context

Missions: Multi-Day Autonomy

A Mission is a high-level business outcome the platform plans, executes, and verifies across hours or days — using multiple Droids.

Mission: "Migrate the billing service off legacy Python 2
          and onto our new Kotlin microservice."

  Day 1  Knowledge Droid  — map call sites, dependencies, contracts
  Day 1  Spec Droid       — produce migration plan + acceptance criteria
  Day 2  Code Droid       — port modules, open staged PRs
  Day 2  Review Droid     — review each PR, flag risks
  Day 3  Code Droid       — address review comments, run integration tests
  Day 3  Coordinator      — verify SLOs, summarize for human approval

Humans stay in the loop at gates: spec approval, PR merge, deploy.

Guardrails & Autonomy Controls

Autonomy Levels

  • Suggest — Droid proposes; human edits and applies
  • Confirm — Droid acts after each-step approval
  • Auto — Droid runs end-to-end; human reviews PR
  • Gated — Auto, but pauses at named checkpoints

Safety Controls

  • Per-repo and per-droid permissions
  • Branch protection — never push to main
  • Secrets redaction in prompts and logs
  • Full audit trail of every tool call
  • Bring-your-own model provider (Anthropic, OpenAI, …)

Sample Workflow: Bug to PR

1. PagerDuty alert  → Incident Droid joins #incident-77
                     → pulls logs, recent deploys, dashboards
                     → posts: "Likely cause: retry storm in
                                   payments-svc commit a3f9c2"

2. Engineer types in Slack:
   "@factory open a fix to cap retries at 3 with backoff."

3. Code Droid  → clones repo, edits payments-svc/retry.go
                → adds unit + integration tests
                → opens PR #2104 with rationale

4. Review Droid  → auto-reviews PR
                  → flags: "Consider exponential jitter"
                  → Code Droid amends in same PR

5. CI green  → engineer merges  → deploy unblocks

Total wall-clock: ~12 minutes from page to merged fix.

Best Practices

1. Start with Suggest mode; promote to Auto as trust grows
2. Write goals as outcomes, not steps ("ship X" not "do A then B")
3. Connect Jira and Slack early — context quality > model quality
4. Use Knowledge Droid before Code Droid on legacy systems
5. Curate the decision log — correct mistakes once, reused forever
6. Pin Droids to specific repos and branches; avoid blast radius
7. Treat Droid PRs like junior-engineer PRs — review, don't rubber-stamp
8. Use Missions for migrations; single delegations for tickets
9. Keep humans on the merge gate for production-touching work
10. Measure outcomes (MTTR, PR cycle time), not lines generated
