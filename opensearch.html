What is OpenSearch?

The Project

  • Distributed search & analytics engine
  • A community-driven, Apache 2.0 fork of Elasticsearch 7.10 + Kibana
  • Forked by AWS in 2021; donated to the Linux Foundation in 2024
  • Two parts: OpenSearch (engine) + OpenSearch Dashboards (UI)
  • Built on Apache Lucene under the hood

What It's For

  • Full-text search — products, docs, code
  • Log analytics — the open ELK stack
  • Observability — metrics, traces, alerts
  • Security analytics — SIEM use cases
  • Vector search — semantic / RAG

Node Roles

  • Cluster manager — cluster state, allocation (formerly "master")
  • Data — stores shards, runs queries
  • Ingest — runs ingest pipelines
  • Coordinating — routes & merges results
  • ML — runs ML / k-NN workloads

Key Ideas

  • Dedicate 3 cluster-manager nodes for quorum
  • Cluster state gossiped to every node
  • Shards rebalance automatically on join/leave
  • Scale out horizontally by adding data nodes

Indices, Shards & Replicas

The Hierarchy

  • Index — a collection of documents (like a table)
  • Shard — an index split into Lucene units
  • Primary — original copy of a shard
  • Replica — copy for HA + read scaling
  • Segment — immutable Lucene file inside a shard

Sizing Rules

  • Target 10–50 GB per shard
  • Primary count is fixed at creation — plan ahead
  • Replicas can change anytime (number_of_replicas)
  • Too many small shards = overhead ("oversharding")
  • Use _split / _shrink to re-shard

Documents & Mappings

# Create an index with an explicit mapping
PUT /products
{
  "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
  "mappings": {
    "properties": {
      "name":        { "type": "text"    },   # analyzed, full-text
      "sku":         { "type": "keyword" },   # exact match / aggregations
      "price":       { "type": "float"   },
      "in_stock":    { "type": "boolean" },
      "created_at":  { "type": "date"    },
      "description": { "type": "text", "analyzer": "english" }
    }
  }
}

text vs keyword is the most important choice: text is tokenized for search, keyword stays exact for filters, sorting, and aggregations. Use a multi-field to get both.

Indexing Documents

Single & Bulk

# Index one document (auto-generated _id)
POST /products/_doc
{ "name": "Trail Shoe", "sku": "TS-9", "price": 89.0 }

# Upsert with a known id
PUT /products/_doc/42
{ "name": "Trail Shoe v2", "price": 99.0 }

# Bulk: NDJSON, one action + one doc per line
POST /_bulk
{ "index": { "_index": "products", "_id": "1" } }
{ "name": "Cap", "price": 19.0 }
{ "index": { "_index": "products", "_id": "2" } }
{ "name": "Socks", "price": 9.0 }

How Writes Work

  • Doc routed to a primary by hash(_id)
  • Written to an in-memory buffer + translog
  • refresh (default 1s) makes it searchable
  • flush commits segments to disk
  • Replicated to replica shards before ack
  • Always prefer _bulk for throughput

The Query DSL

GET /products/_search
{
  "query": {
    "bool": {
      "must":   [ { "match": { "name": "trail shoe" } } ],   # relevance
      "filter": [ { "range": { "price": { "lte": 100 } } },  # yes/no, cached
                  { "term":  { "in_stock": true } } ],
      "should": [ { "match": { "description": "waterproof" } } ],
      "must_not":[ { "term": { "sku": "TS-0" } } ]
    }
  },
  "from": 0, "size": 10,
  "sort": [ { "_score": "desc" }, { "price": "asc" } ]
}

query context (must/should) scores relevance; filter context (filter/must_not) is a cached yes/no with no scoring — faster, so push exact constraints there.

Aggregations

GET /orders/_search
{
  "size": 0,                       # only want aggregates, not hits
  "aggs": {
    "by_status": {                 # bucket aggregation
      "terms": { "field": "status" },
      "aggs": {
        "revenue": { "sum": { "field": "total" } },     # metric
        "avg_total": { "avg": { "field": "total" } }
      }
    },
    "daily": {                     # time-series buckets
      "date_histogram": { "field": "created_at", "calendar_interval": "day" }
    }
  }
}

Bucket aggregations group documents; metric aggregations compute numbers; pipeline aggregations run on other aggregations' output. Nest them to build analytics in one request.

Ingest Pipelines

# Define a pipeline of processors that transform docs at index time
PUT /_ingest/pipeline/weblogs
{
  "description": "Parse and enrich access logs",
  "processors": [
    { "grok":   { "field": "message",
                  "patterns": ["%{COMBINEDAPACHELOG}"] } },
    { "date":   { "field": "timestamp",
                  "formats": ["dd/MMM/yyyy:HH:mm:ss Z"] } },
    { "geoip":  { "field": "clientip", "target_field": "geo" } },
    { "remove": { "field": "message" } }
  ]
}

# Use it on write
POST /weblogs/_doc?pipeline=weblogs
{ "message": "127.0.0.1 - - [10/Oct/2024:13:55:36 +0000] ..." }

Data Prepper and Logstash/Fluent Bit handle heavier ETL upstream; ingest pipelines handle lightweight enrichment inside the cluster.

Index State Management (ISM)

Lifecycle Policies

  • Automate index lifecycle by state
  • States have actions + transitions
  • hot → warm → cold → delete
  • Actions: rollover, force_merge, replica_count, snapshot, delete

Rollover & Data Streams

  • Rollover — new index at a size/age/doc threshold
  • Data streams — append-only time series over backing indices
  • Write to one alias, read across all
  • Pairs with UltraWarm + cold storage on managed services

Vector & Semantic Search (k-NN)

PUT /docs
{
  "settings": { "index.knn": true },
  "mappings": { "properties": {
    "embedding": {
      "type": "knn_vector", "dimension": 768,
      "method": { "name": "hnsw", "engine": "lucene",
                  "space_type": "cosinesimil" }
    }
  }}
}

# Approximate nearest-neighbor query
GET /docs/_search
{ "query": { "knn": { "embedding": { "vector": [0.12, ...], "k": 10 } } } }

HNSW graphs power approximate k-NN over Lucene/Faiss/nmslib engines. The ML Commons + neural-search plugins auto-generate embeddings and run hybrid (BM25 + vector) queries — the backbone of RAG on OpenSearch.

Snapshots & Restore

# Register a snapshot repository (S3, fs, GCS, Azure)
PUT /_snapshot/backups
{ "type": "s3", "settings": { "bucket": "my-os-backups", "region": "us-east-1" } }

# Take a snapshot (incremental after the first)
PUT /_snapshot/backups/snap-2024-10-10?wait_for_completion=false
{ "indices": "products,orders", "include_global_state": false }

# Restore into the cluster
POST /_snapshot/backups/snap-2024-10-10/_restore
{ "indices": "products", "rename_pattern": "products",
  "rename_replacement": "products_restored" }

Snapshots are incremental at the segment level, so repeat backups are cheap. Automate them with the Snapshot Management plugin or an ISM snapshot action.

Performance & Sharding Strategy

Shard Sizing

Keep shards 10–50 GB. Aim for < 25 shards per GB of JVM heap per node to avoid overhead.

Heap & Memory

Set JVM heap to ~50% of RAM, max ~32 GB. Leave the rest for the Lucene filesystem cache.

Bulk & Refresh

Batch with _bulk; raise refresh_interval (e.g. 30s) during heavy ingest to cut segment churn.

Read Path

Use filter context for cacheable constraints, force_merge read-only indices, and _search profiling to find slow queries.

Operating a Cluster

Health & Monitoring

GET /_cluster/health           # green/yellow/red
GET /_cat/nodes?v              # node roles, heap, CPU
GET /_cat/shards?v             # shard allocation
GET /_cat/indices?v&s=store.size:desc
GET /_nodes/stats/jvm,os       # heap, GC, load
  • green all shards assigned
  • yellow replicas unassigned
  • red a primary is missing

Scaling & Resilience

  • Add data nodes → shards rebalance
  • Use shard allocation awareness across AZs
  • Cross-cluster replication for DR
  • Do rolling upgrades; one node at a time
  • Managed options: Amazon OpenSearch Service, Aiven

Best Practices

1. Design mappings explicitly — disable dynamic mapping in prod
2. Use keyword for filters/aggs, text for full-text
3. Always index in bulk; tune refresh during heavy ingest
4. Keep shards 10–50 GB; avoid oversharding
5. Put exact constraints in filter context for caching
6. Use ISM + data streams for time-series data
7. Run 3 dedicated cluster-manager nodes for quorum
8. Enable the security plugin — TLS, RBAC, audit logs
9. Automate snapshots to remote object storage
10. Watch heap, GC, and cluster health continuously
