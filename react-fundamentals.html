React Fundamentals

Components, props, state, and the core hooks — for developers who already know JavaScript

React JSX Hooks

What React is

A UI library, not a framework

  • You write functions that return markup
  • React updates the DOM when data changes
  • You do not query or mutate nodes yourself
  • Routing, data fetching, and build tools are separate choices

Why teams pick it

  • Declarative: describe the UI for the current data
  • Composition: small components nest into screens
  • One-way data: props down, events up
  • The same mental model scales from a button to an app

If you can write a JavaScript function that takes data and returns HTML-shaped output, you can write React.

The contract

Given the same props and state, a component should return the same UI. React re-runs the function after state changes, diffs the result, and patches the DOM.

What you stop doing

No document.querySelector to flip classes. No keeping a parallel copy of the UI in variables. Change the data; let React render the next view.

JSX

JSX looks like HTML inside JavaScript. A bundler (or TypeScript) compiles it to function calls. It is an expression, so you can nest it in return, ternaries, and .map().

function Greeting({ name }) {
  return (
    <section className="hero">
      <h1>Hello, {name}</h1>
      <p>Today is {new Date().toDateString()}</p>
    </section>
  );
}

className, not class

class is reserved in JS. Use className, htmlFor, and camelCase style objects.

One parent

A return must be one tree. Wrap siblings in a <div> or a fragment <>...</>.

Functional components

A component is a function

function Button({ label }) {
  return <button type="button">{label}</button>;
}

export default function App() {
  return (
    <main>
      <Button label="Save" />
    </main>
  );
}

Rules that stick

  • Name starts with a capital letter — Button, not button
  • Return JSX (or null to render nothing)
  • Receive one argument: a props object
  • Do not mutate props; treat them as read-only
  • Prefer function declarations or arrow functions — both are valid

Props

Props are the function arguments of a component. The parent passes values; the child reads them. Data flows down.

function UserCard({ name, role = "member", active }) {
  return (
    <article>
      <h3>{name}</h3>
      <p>{role}{active ? " · online" : ""}</p>
    </article>
  );
}

<UserCard name="Ada" role="admin" active={true} />

Strings vs expressions

name="Ada" is a string. Anything else uses curly braces: active={true}, count={n}, onSave={save}.

Defaults

Destructure with defaults (role = "member") so the child stays usable when a parent omits a prop.

Component composition

Nest, don't copy

function Panel({ title, children }) {
  return (
    <section className="panel">
      <h2>{title}</h2>
      {children}
    </section>
  );
}

function Dashboard() {
  return (
    <Panel title="Inbox">
      <MessageList />
      <ComposeBox />
    </Panel>
  );
}

How screens are built

  • children is a prop: whatever you nest between the tags
  • Small pieces (Avatar, Badge) combine into pages
  • Pass data down; lift shared state up to the nearest common parent
  • If two siblings need the same value, that value lives in the parent

Event handling

function SearchBox({ onSearch }) {
  function handleSubmit(event) {
    event.preventDefault();
    const q = new FormData(event.currentTarget).get("q");
    onSearch(String(q ?? ""));
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="q" placeholder="Search" />
      <button type="submit">Go</button>
    </form>
  );
}

camelCase props

onClick, onChange, onSubmit — you pass a function, not a string. React calls it with a synthetic event.

Events go up

The child calls onSearch(q). The parent owns the data. That is props-down, events-up.

State with useState

useState is data that belongs to the component and survives re-renders. Changing it asks React to render again.

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Clicked {count} times</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}

The array is [currentValue, setter]. The argument to useState is the initial value, used only on the first render. Hooks must be called at the top of the function — not inside if, loops, or nested functions.

Updating state correctly

Replace, don't mutate

const [user, setUser] = useState({ name: "Ada" });

// wrong: mutates the same object
user.name = "Grace";
setUser(user);

// right: new object
setUser({ ...user, name: "Grace" });

React compares by identity. Mutating in place can skip a render.

Next value from previous

setCount(c => c + 1);
setItems(items => [...items, next]);

Use the updater function when the new value depends on the old one, especially if you call the setter more than once in the same event.

Conditional rendering

function Inbox({ messages, isLoading, error }) {
  if (isLoading) return <p>Loading…</p>;
  if (error) return <p role="alert">{error}</p>;

  return (
    <section>
      {messages.length === 0 ? (
        <p>Inbox is empty</p>
      ) : (
        <MessageList messages={messages} />
      )}
      {user?.isAdmin && <ModerationBar />}
    </section>
  );
}

Three patterns

Early return for exclusive screens. Ternary when both branches are JSX. && when you show a piece or nothing.

Watch zeros

{count && <Badge />} renders 0 when count is 0. Prefer count > 0 && or a ternary.

Lists and keys

function MessageList({ messages }) {
  return (
    <ul>
      {messages.map((msg) => (
        <li key={msg.id}>
          <strong>{msg.from}</strong> {msg.body}
        </li>
      ))}
    </ul>
  );
}

Why key exists

React matches list items across renders. A stable key (usually an id) tells it which item is which when the array is filtered, sorted, or inserted into.

What not to use

Index as key is a last resort. If the list reorders, index keys attach state to the wrong row. Never use a random value — it remounts every render.

useEffect

useEffect runs after paint to sync with something outside React: the network, document.title, a subscription, a timer.

import { useEffect, useState } from "react";

function UserBadge({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    let cancelled = false;
    fetch(`/api/users/${userId}`)
      .then((r) => r.json())
      .then((data) => { if (!cancelled) setUser(data); });
    return () => { cancelled = true; };
  }, [userId]);

  if (!user) return <p>Loading…</p>;
  return <p>{user.name}</p>;
}

If you can compute it during render from props and state, you do not need an effect. Effects are for the outside world.

Effect dependencies and cleanup

The dependency array

  • [userId] — re-run when userId changes
  • [] — run once after mount
  • Omitted — run after every render (rarely what you want)

List every value from the component that the effect reads. Missing deps cause stale closures.

Cleanup

Return a function to undo the subscription, timer, or in-flight work. React runs it before the next effect and on unmount.

useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);

useContext

Context lets a distant ancestor pass a value without threading props through every layer. Use it for theme, locale, current user — not for every piece of state.

import { createContext, useContext } from "react";

const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Page />
    </ThemeContext.Provider>
  );
}

function ThemedButton() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>Save</button>;
}

A consumer re-renders when the value identity changes. Keep the provided value stable (or wrap it in state) so you do not refresh the whole tree on every parent render.

A small tree, put together

function NoteApp() {
  const [items, setItems] = useState([]);
  const [draft, setDraft] = useState("");

  function add(event) {
    event.preventDefault();
    if (!draft.trim()) return;
    setItems((list) => [...list, { id: crypto.randomUUID(), text: draft }]);
    setDraft("");
  }

  return (
    <>
      <form onSubmit={add}>
        <input value={draft} onChange={(e) => setDraft(e.target.value)} />
        <button type="submit">Add</button>
      </form>
      <ul>
        {items.map((item) => (
          <li key={item.id}>{item.text}</li>
        ))}
      </ul>
    </>
  );
}

Controlled input (value + onChange), state updates, a list with keys, and composition in one component. Split NoteForm / NoteList when the file gets hard to scan.

Common pitfalls

1. Mutating state or props instead of creating a new array/object
2. Using the array index as key on a list that reorders
3. Calling hooks inside conditions — the order must be identical every render
4. Forgetting the dependency array on useEffect (or omitting a value it reads)
5. Fetching in an effect with no cleanup, then setting state after unmount
6. {count && ...} rendering a literal 0
7. Passing a new object as context value every render and refreshing every consumer
8. Reaching for context (or a store) when a parent prop would do

Practices that keep UIs honest

1. One component, one job; compose with children
2. Lift state to the nearest shared parent; pass setters or callbacks down
3. Prefer derived values during render over copying props into state
4. Keys from stable ids; never from Math.random()
5. Effects sync outward; if it is just math on props, skip the effect
6. Controlled inputs when React must own the value
7. Name event props onSomething so the data-flow direction is obvious
8. Keep context for wide, slow-changing values (theme, auth), not every field
