Multi-Model LLM APIs

One interface, many models — Bedrock, Vertex, Foundry, OpenRouter, LiteLLM and the gateways in between

The fragmentation tax

What it looks like in code

Every provider once had its own request envelope. Claude wants messages + max_tokens. Gemini wants contents + parts. Cohere, Mistral and Titan each invented something else.

Supporting two models side by side means a serializer and a parser per family — plus per-provider auth, retry semantics, error codes, rate-limit headers and streaming formats.

What it costs you

Switching cost. A better/cheaper model ships and you can't adopt it in a sprint.

Blast radius. One provider outage takes the product down because there is no second path.

No cost ownership. Five teams, five API keys, five invoices, zero attribution.

Governance drift. PII filtering lives in whichever prompt someone remembered to write it into.

The multi-model API layer exists to turn model choice into a config change instead of a refactor.

Four lanes, not one market

1. Hyperscaler platform

Bedrock · Vertex AI · Azure AI Foundry

Models inside your existing cloud boundary. IAM, VPC, audit trail, one invoice.

2. Aggregator

OpenRouter · Together · Fireworks

Hundreds of models, one key, one balance. Fastest path to breadth.

3. Self-hosted gateway

LiteLLM · Portkey · Kong AI GW · Bifrost

You own the control plane: keys, budgets, fallbacks, logs. Providers stay yours.

4. Self-hosted inference

vLLM · SGLang · TGI · Ollama

Open weights on your GPUs, exposed as an OpenAI-shaped endpoint.

These stack: vLLM behind LiteLLM, with Bedrock and OpenRouter as fallback pools.

What "unified" actually normalizes

Normalized reliably

✓ Message/turn structure and system prompts

✓ Common inference params — maxTokens, temperature, topP, stop sequences

✓ Token usage and stop reason

✓ Streaming envelope

✓ Basic tool/function-call schemas

✓ Multimodal image + document blocks

Leaks through anyway

✗ Extended thinking / reasoning-effort controls

✗ Prompt-cache breakpoints and TTL rules

✗ Citations, structured outputs, JSON-schema modes

✗ Context limits and per-model tokenizers

✗ Safety-refusal behaviour and error taxonomies

✗ Prompts themselves — a prompt tuned for one family is not portable

Design rule: the API is portable, the behaviour is not. Budget for re-evaluation on every model swap.

Amazon Bedrock — the surface

Two planes

bedrock — control plane. Model access, guardrails, custom models, provisioned throughput, batch jobs.

bedrock-runtime — data plane. Converse, ConverseStream, InvokeModel, InvokeModelWithResponseStream.

IAM permission that matters: bedrock:InvokeModel — Converse rides on it.

Why teams pick it

No new trust boundary. Same IAM, VPC endpoints, CloudTrail, KMS, Organizations SCPs you already audit.

One contract. Anthropic, Meta, Mistral, Cohere, DeepSeek, Stability and Amazon's own Nova/Titan on one bill.

Swappability. modelId is a string. Changing models is a config change, not a rewrite.

The Converse API

AWS's answer to per-provider payloads: one request shape, one response envelope, any model.

Request

{
  "modelId": "<id | profile | ARN>",   // URI param
  "messages": [ {role, content[]} ],
  "system":   [ {text} ],
  "inferenceConfig": {
    "maxTokens": 2048, "temperature": 0.2
  },
  "toolConfig": { "tools": [...],
                  "toolChoice": {...} },
  "guardrailConfig": {
    "guardrailIdentifier": "...",
    "guardrailVersion": "1", "trace": "enabled"
  },
  "additionalModelRequestFields": { ... }
}

Response

{
  "output": { "message": {role, content[]} },
  "stopReason": "end_turn | tool_use |
                 max_tokens | guardrail_intervened",
  "usage":   { inputTokens, outputTokens,
               cacheReadInputTokens, ... },
  "metrics": { "latencyMs": 812 }
}

The escape hatch: additionalModelRequestFields passes model-native params the common schema doesn't cover. Reach for it knowingly — it is where portability ends.

Converse in three languages

Python (boto3)

import boto3
br = boto3.client("bedrock-runtime",
                  region_name="eu-central-1")

r = br.converse(
  modelId="eu.anthropic.claude-sonnet-4-5-v1:0",
  messages=[{"role": "user",
             "content": [{"text": "Summarise this ticket"}]}],
  system=[{"text": "You are a support triage assistant."}],
  inferenceConfig={"maxTokens": 512, "temperature": 0.2},
)
print(r["output"]["message"]["content"][0]["text"])
print(r["usage"], r["metrics"]["latencyMs"])

.NET (AWS SDK v3)

var client = new AmazonBedrockRuntimeClient();

var resp = await client.ConverseAsync(new ConverseRequest {
  ModelId = "eu.anthropic.claude-sonnet-4-5-v1:0",
  Messages = { new Message {
      Role = ConversationRole.User,
      Content = { new ContentBlock { Text = "Summarise this ticket" } }
  }},
  InferenceConfig = new InferenceConfiguration {
      MaxTokens = 512, Temperature = 0.2f }
});

Console.WriteLine(resp.Output.Message.Content[0].Text);

ConverseStreamAsync returns the same envelope as an async event stream — identical field names, chunked.

The single most misunderstood field in Bedrock. It accepts five different kinds of identifier.

Bedrock production levers

Guardrails

Content filters, denied topics, PII redaction, contextual grounding — enforced at the API layer, not in a prompt. Attach via guardrailConfig; stopReason tells you when it fired.

Prompt caching

Cache stable prefixes across calls. Order matters: longer-TTL breakpoints must appear before shorter ones. Stable content early, dynamic content late.

Batch inference

Since Feb 2026 batch accepts the Converse format too — same request shape for realtime and offline. Big discount, hours of latency.

Provisioned throughput

Committed model units for guaranteed TPS. Expensive and inflexible — only after you have a measured, steady load curve.

Intelligent Prompt Routing

What it is

Point modelId at a router ARN instead of a model. Bedrock predicts per-request which of two models in a family will answer acceptably and sends the easy ones to the cheap model.

GA since April 2025: pick any two models from a family and set the routing criteria. AWS quotes up to ~30% cost reduction on mixed workloads.

When it is the wrong tool

✗ Cross-family routing — it routes within a family only. Claude↔Llama needs your own layer.

✗ Deterministic behaviour — two models means two prompt sensitivities and two eval baselines.

✗ Tight latency SLOs — classification adds a hop.

Cheaper first move: a static cascade you control. Small model attempts, escalate on low confidence or schema-validation failure.

Google Vertex AI Model Garden

Shape of it

~200+ curated models — Gemini first-party, Gemma open weights, plus Claude, Llama and Mistral as partner models.

Native generateContent API, plus an OpenAI-compatible endpoint that makes the OpenAI SDK work unchanged.

Auth via Google Cloud IAM / service accounts; DLP for data controls.

Where it wins

Data gravity. BigQuery, Vertex AI Search and GCS in the same project — grounding pipelines are short.

Long-context multimodal. Gemini's video/audio handling has no direct Bedrock equivalent.

Tuning path. Fastest managed custom-training loop of the three.

Trade-off: no OpenAI frontier models, ever.

Azure AI Foundry

Shape of it

The renamed Azure AI Studio. Largest catalog of the three by a wide margin — GPT family, Llama, Mistral, DeepSeek, Qwen, Phi, Cohere, Grok, Stability, plus Anthropic via partnership.

Two deployment shapes: serverless per-token endpoints and managed compute for open weights you host in your subscription.

Where it wins

OpenAI depth. Frontier GPT releases land on Foundry at or near launch — and for many regulated enterprises Azure-OpenAI is approved where OpenAI-direct is not.

Identity + governance. Entra ID, Purview, Defender. If your org already runs on Microsoft 365, the approval path is already paved.

OpenRouter — the aggregator lane

Mechanics

One OpenAI-compatible base URL, one key, one balance, 300+ models. Change model from anthropic/claude-... to google/gemini-... and you are done.

{
  "model": "openai/gpt-5.5",
  "models": ["anthropic/claude-...", "..."],  // fallbacks
  "provider": {
    "order": ["openai", "azure"],
    "allow_fallbacks": false,
    "max_price": { "prompt": 3, "completion": 15 }
  }
}

Read the fine print

Fees. Credit-purchase fee on top of token cost; BYOK is free up to a monthly request threshold, then a percentage of the equivalent platform cost.

BYOK reorders routing. Your own key takes priority over the order array you set. Pin with "always use for this provider" if that matters.

Governance ceiling. No public SLA, and a third party sits in the prompt path. Verify ZDR settings before regulated traffic.

Best use: evaluation and breadth. Weakest use: your one high-volume production path.

LiteLLM — the open-source gateway

config.yaml is the product

model_list:
  - model_name: fast          # alias your apps call
    litellm_params:
      model: bedrock/eu.anthropic.claude-haiku-...
      aws_region_name: eu-central-1
  - model_name: fast          # same alias = load balanced
    litellm_params:
      model: azure/gpt-5-mini
      api_base: os.environ/AZURE_BASE
  - model_name: local
    litellm_params:
      model: hosted_vllm/qwen3-32b
      api_base: http://vllm.internal:8000/v1

router_settings:
  routing_strategy: latency-based-routing
  fallbacks: [{ "fast": ["local"] }]
  num_retries: 2

What you get

✓ One OpenAI-shaped endpoint over 100+ providers — apps change base_url and nothing else

✓ Virtual keys per team with hard budgets; 429 on exhaustion

✓ Load balancing, fallback chains, retries, Redis caching

✓ Cost attribution per key/team/tag, exportable for chargeback

✓ MIT-licensed, self-hosted — only providers see prompts, only you see provider credentials

Cost of ownership: Postgres for keys/spend, Redis for routing state, and you own the patching.

Why bother

Data never leaves your network. Marginal cost per token approaches zero once GPUs are paid for. No rate limits, no deprecation notices, full control of the model version.

Ollama for laptops and single-node dev; vLLM or SGLang for serving throughput; TGI if you are already in the HF ecosystem.

Why it hurts

GPU capacity planning, quantization trade-offs, KV-cache tuning, model-version rollouts, and someone on call for it. Utilization below ~40% and the hyperscaler was cheaper.

The winning pattern is hybrid: cheap high-volume classification local, frontier reasoning in the cloud, one alias namespace over both.

Routing strategies

Static alias

App calls fast / smart / cheap; config maps them to models. Boring, debuggable, covers ~80% of real need.

Load balance

Multiple deployments under one alias, picked by lowest latency, least busy, or weighted RPM. Also your throttle escape valve.

Cascade

Cheap model first; escalate on schema-validation failure, low self-reported confidence, or a judge check. Largest reliable cost win.

Classifier / semantic

A small model or embedding lookup picks the target per request. Real gains, real complexity — measure before you build it.

Every routing layer is a new failure mode. Prove the savings with a spend report before adding one.

Failure handling

What actually breaks

429 throttling — the most common by far. Regional capacity, not your account, is usually the constraint.

5xx / stream aborts mid-generation — partial output already sent to the user.

Context-window overrun on a model swap that has a smaller window.

Guardrail interventions returning a non-answer that your parser wasn't expecting.

The pattern

1. Cross-region inference profile before anything else — free throughput.

2. Retry with jitter on 429/503; cap at 2–3.

3. Fallback chain across providers, not just models — an outage is rarely one model.

4. Per-request timeout budget, and degrade gracefully: cached answer, smaller model, or an honest error.

5. Circuit-break a provider after N consecutive failures instead of retrying into a wall.

Cost governance

Controls that hold

Virtual keys per team with a hard monthly cap. Exhaustion returns 429, not a surprise invoice.

Tag every request with team, feature and environment — attribution is impossible to retrofit.

Prompt caching on stable system prompts and retrieved documents. The single biggest lever on RAG-shaped traffic.

Batch anything not user-facing.

Measure the right unit

Cost per session or per resolved task, not per request. An agent loop is 20 calls; a request-level dashboard will lie to you.

Watch the ratio of cache-read to fresh input tokens — it tells you whether your caching is actually landing.

Rough rule of thumb: below ~5M requests/month a managed gateway usually beats self-hosting once labour is priced in. Above ~50M the maths inverts hard.

Observability and evals

Instrument at the gateway

OpenTelemetry GenAI semantic conventions give you spans with model, token counts, latency and cost as attributes — feeding the same Grafana/Datadog you already run.

Per-call trace: alias requested → model actually served → retries → fallback taken → guardrail verdict. Without that chain, "why was this answer bad" is unanswerable.

Langfuse / Phoenix / MLflow for prompt-level traces and datasets.

Evals are the real portability test

A model swap is only safe if you can prove it. Keep a golden set of 100–500 real cases per critical path, versioned with the prompt, run in CI.

Gate on task success, not vibes: schema validity, factual match, refusal rate, p95 latency, cost per task.

Rule: no model change ships without an eval diff. This is the discipline that makes the whole multi-model story worth having.

The anti-pattern: building a routing abstraction on day one for a product that calls one model. Abstract when you have the second provider, not before.

Best practices

1. Call models by alias (fast, smart) — never hardcode a model ID in application code
2. Use cross-region inference profiles in production; it is the cheapest throughput you will ever get
3. Treat additionalModelRequestFields as a portability debt marker — log every use
4. Version prompts alongside the golden eval set; gate model swaps on the eval diff in CI
5. Enforce guardrails at the API layer, not inside prompts — prompts are not a security boundary
6. Give every team a virtual key with a hard budget before the first invoice, not after
7. Fallback across providers, not just models — correlated failures are the norm
8. Structure prompts cache-first: stable system + documents early, user turn last
9. Track cost per resolved task; request-level dashboards hide agent-loop blowups
10. Re-run the decision every two quarters — pricing, catalogs and capability gaps all move faster than your architecture does
