Open-source SIEM & XDR — from raw logs to real alerts

What Is a SIEM?

The Problem

  • Every server, firewall, and laptop writes its own logs
  • Those logs live in a hundred different places
  • Nobody reads them until after something goes wrong
  • An attacker who gets in can sit unnoticed for weeks
  • Auditors ask "prove it" and you have nothing to show

What a SIEM Does

  • Collect — pull logs from everywhere into one place
  • Normalize — turn messy text into structured fields
  • Correlate — spot patterns across many events
  • Alert — tell a human when it matters
  • Retain — keep searchable history for audits

SIEM watches the logs. XDR also watches the endpoint itself — files, processes, configuration — and can act. Wazuh does both.

What Is Wazuh?

The Short Version

  • Free and open source, licensed GPLv2
  • Forked from the OSSEC host-IDS project in 2015
  • Grew into a unified SIEM + XDR platform
  • Agent-based — a small daemon runs on each endpoint
  • No per-GB licence fee — you pay in hardware and time

What You Get Out of the Box

  • Log collection and rule-based detection
  • File Integrity Monitoring (FIM)
  • Vulnerability detection
  • Security Configuration Assessment (CIS benchmarks)
  • Rootkit and malware detection
  • Active Response — automatic countermeasures
  • MITRE ATT&CK and compliance mapping

The Four Components

Wazuh Agent

Runs on the endpoint you want to watch — Linux, Windows, macOS, AIX, Solaris. Reads logs, checks files, inventories software, and ships it all to the server. Lightweight, typically a few tens of MB of RAM.

Wazuh Server

Also called the manager. Receives agent data, runs it through decoders and rules, and generates alerts. Config lives in /var/ossec/. Can be clustered as master + workers.

Wazuh Indexer

A fork of OpenSearch. Stores and indexes alerts so they can be searched fast. This is where your retention and disk sizing live.

Wazuh Dashboard

A fork of OpenSearch Dashboards. The web UI for hunting through alerts, viewing compliance reports, and managing agents.

# The path a single event takes
raw log line on the endpoint
  -> agent reads it, forwards over an encrypted channel  (tcp/1514)
  -> server decodes it into fields          (analysisd)
  -> server matches it against the ruleset  (rule fires -> alert)
  -> alert written to /var/ossec/logs/alerts/alerts.json
  -> Filebeat ships alerts.json to the indexer            (tcp/9200)
  -> indexed into wazuh-alerts-4.x-YYYY.MM.DD
  -> you search it in the dashboard                       (tcp/443)

# Other ports worth knowing
tcp/1515   agent enrollment (wazuh-authd)
tcp/1516   cluster traffic between master and workers
tcp/55000  Wazuh RESTful API

If an event never fires a rule, no alert is stored. Detection happens on the server, not in the dashboard.

Deploying Wazuh

Pick a Topology

  • All-in-one — server, indexer, dashboard on one box. Fine for labs and small estates.
  • Distributed — each component on its own host. The normal production choice.
  • Clustered — one master plus workers for many agents; indexer gets multiple nodes.
  • Docker / Kubernetes — official compose files and Helm charts.

Rough starting point: 4 vCPU / 8 GB is enough to try it. Plan real capacity from events per second and how long you must retain.

Quickstart (All-in-One)

# On a clean Ubuntu/RHEL host, as root
curl -sO https://packages.wazuh.com/4.x/wazuh-install.sh
bash ./wazuh-install.sh -a

# The script prints the admin password at the end.
# Then browse to https://<server-ip>

# Check the services
/var/ossec/bin/wazuh-control status
systemctl status wazuh-indexer wazuh-dashboard

The assistant installs all four components, generates certificates, and wires them together.

The Wazuh Agent

What It Actually Does

  • Tails log files and Windows event channels
  • Hashes watched files to detect changes (FIM)
  • Inventories installed packages, ports, processes
  • Runs configuration checks against benchmarks
  • Executes Active Response scripts when told to

Each capability is a module, switched on or off in ossec.conf.

Where Things Live

/var/ossec/etc/ossec.conf      # main config
/var/ossec/etc/rules/          # custom rules
/var/ossec/etc/decoders/       # custom decoders
/var/ossec/logs/ossec.log      # agent's own log
/var/ossec/bin/wazuh-control   # start/stop/status

# Windows
C:\Program Files (x86)\ossec-agent\ossec.conf

On Windows the agent is a service; on Linux it is a set of daemons under wazuh-control.

Enrolling & Grouping Agents

# 1. Install the agent, pointing it at the manager
WAZUH_MANAGER="10.0.0.5" apt install wazuh-agent

# 2. Enroll it (the agent asks the manager for a key, over tcp/1515)
/var/ossec/bin/agent-auth -m 10.0.0.5
systemctl restart wazuh-agent

# 3. Confirm on the manager
/var/ossec/bin/agent_control -l
#   ID: 001, Name: web-01, IP: any, Active

# 4. Put agents into groups so they share configuration
/var/ossec/bin/agent_groups -a -g linux-servers -i 001

A group's shared config lives in /var/ossec/etc/shared/<group>/agent.conf and is pushed to every member automatically.

<!-- agent.conf for the linux-servers group -->
<agent_config>
  <syscheck>
    <directories check_all="yes" realtime="yes">/etc,/usr/bin</directories>
  </syscheck>
</agent_config>

Configure by group, not by hand on each box. It is the difference between managing 10 agents and 1,000.

Collecting Logs

<!-- Each source is a <localfile> block in ossec.conf -->

<!-- A plain text log -->
<localfile>
  <log_format>syslog</log_format>
  <location>/var/log/auth.log</location>
</localfile>

<!-- Anything that writes JSON lines -->
<localfile>
  <log_format>json</log_format>
  <location>/var/log/myapp/events.json</location>
</localfile>

<!-- Windows: read an event channel directly -->
<localfile>
  <log_format>eventchannel</log_format>
  <location>Security</location>
</localfile>

<!-- Run a command and treat its output as a log -->
<localfile>
  <log_format>command</log_format>
  <command>df -P</command>
  <frequency>360</frequency>
</localfile>

Devices that cannot run an agent — firewalls, switches, appliances — can send syslog over the network to the manager instead, configured with a <remote> block.

Decoders — From Raw Log to Fields

A decoder's only job is to pull named fields out of a line of text. Rules then match on those fields.

# The raw line
Jan 14 09:12:44 web-01 sshd[2211]: Failed password for root from 203.0.113.9 port 55123 ssh2

# After decoding
program_name : sshd
srcuser      : root
srcip        : 203.0.113.9
srcport      : 55123

# Test it yourself — paste a log line into:
/var/ossec/bin/wazuh-logtest

Wazuh ships with hundreds of decoders already. You only write one when your application's format is not recognised:

<!-- /var/ossec/etc/decoders/local_decoder.xml -->
<decoder name="myapp">
  <prematch>^myapp: </prematch>
</decoder>

<decoder name="myapp-login-fail">
  <parent>myapp</parent>
  <regex>login failed for (\w+) from (\d+.\d+.\d+.\d+)</regex>
  <order>srcuser, srcip</order>
</decoder>

Rules & Alert Levels

Every rule carries a level from 0 to 16. The level is how you say "how much should a human care?"

LevelMeaningExample
0Ignored — no alert at allNoise you have deliberately silenced
3Successful / authorised eventA user logged in normally
5User-generated errorOne failed password
7Suspicious pattern in the messageKnown-bad string appears in a log
10Repeated errors from one sourceSeveral failed logins in a row
12High-importance eventSystem error, config change
14High-importance security eventBrute-force pattern confirmed
15Severe attackActive exploitation indicators

By default the manager stores alerts at level 3 and above (<log_alert_level>3</log_alert_level>). Raise it if you are drowning; lower it if you are hunting.

Writing Your First Custom Rule

<!-- /var/ossec/etc/rules/local_rules.xml
     Use IDs from 100000 upward. Everything below is reserved
     for the official ruleset and will be overwritten on upgrade. -->

<group name="myapp,">

  <!-- Fire on a single failed login -->
  <rule id="100001" level="5">
    <decoded_as>myapp</decoded_as>
    <match>login failed</match>
    <description>myapp: failed login for $(srcuser)</description>
  </rule>

  <!-- Correlate: 6 of those from one IP within 2 minutes -->
  <rule id="100002" level="10" frequency="6" timeframe="120">
    <if_matched_sid>100001</if_matched_sid>
    <same_source_ip />
    <description>myapp: brute force from $(srcip)</description>
  </rule>

</group>

Then always test before restarting:

/var/ossec/bin/wazuh-logtest        # paste a sample line, see which rule fires
systemctl restart wazuh-manager

frequency + timeframe + same_source_ip is the whole idea of correlation: one failure is noise, six is an attack.

File Integrity Monitoring

What FIM Watches

  • Files created, modified, or deleted
  • Changes to size, permissions, owner, and hashes
  • Who made the change, if whodata is on
  • Windows registry keys as well as files

Alert IDs to remember: 550 modified, 553 deleted, 554 added.

Configuring It

<syscheck>
  <frequency>43200</frequency>

  <!-- scan on a schedule -->
  <directories check_all="yes">/etc,/bin</directories>

  <!-- react the instant it changes -->
  <directories check_all="yes" realtime="yes">
    /var/www
  </directories>

  <!-- also record which user did it -->
  <directories check_all="yes" whodata="yes">
    /etc/ssh
  </directories>

  <ignore>/etc/mtab</ignore>
  <ignore type="sregex">.log$</ignore>
</syscheck>

realtime uses inotify on Linux. whodata hooks auditd, which costs more but answers "who changed it" — usually the question you actually have.

Security Configuration Assessment

The Idea

  • Most breaches start with a bad setting, not a zero-day
  • SCA checks each endpoint against a hardening policy
  • Policies ship for CIS benchmarks: Linux distros, Windows, Docker
  • Each check is pass / fail / not applicable, with a remediation note
  • Runs on the agent, on a schedule — no separate scanner needed

Turning It On

<sca>
  <enabled>yes</enabled>
  <scan_on_start>yes</scan_on_start>
  <interval>12h</interval>
</sca>

Policy files live in /var/ossec/ruleset/sca/. Results appear per-agent in the dashboard with an overall score.

Typical findings: SSH root login permitted, no password ageing, world-writable directories, unnecessary services running.

Vulnerability Detection

Syscollector
inventories packages
→
Server
matches inventory
against CVE feed
→
Dashboard
CVE list per agent

Wazuh does not scan your network. The agent reports what is installed; the server compares that inventory against vulnerability data and tells you which CVEs apply.

<!-- The agent must inventory software for this to work -->
<wodle name="syscollector">
  <disabled>no</disabled>
  <interval>1h</interval>
  <packages>yes</packages>
  <os>yes</os>
  <ports all="no">yes</ports>
</wodle>

<!-- And the server must have detection enabled -->
<vulnerability-detection>
  <enabled>yes</enabled>
</vulnerability-detection>

Because it is inventory-based it is quiet and cheap — no scanning traffic, no credentialed scans, no scan windows. The trade-off is that it only sees packages the OS knows about.

Malware & Rootkit Detection

Rootcheck

The built-in anomaly scanner. Looks for hidden processes and ports, files owned by root in odd places, and known rootkit signatures.

VirusTotal

Chain it to FIM: when a new file appears, send its hash to VirusTotal and alert if it is flagged. Needs an API key.

YARA

Run YARA rules against files that FIM reports, triggered through Active Response. Catches known malware families by content, not hash.

Command Monitoring

Schedule any command and alert when its output changes — a simple way to watch for things the built-in modules miss.

<!-- VirusTotal lookup on every file FIM reports -->
<integration>
  <name>virustotal</name>
  <api_key>YOUR_API_KEY</api_key>
  <group>syscheck</group>
  <alert_format>json</alert_format>
</integration>

Active Response

Active Response lets Wazuh act on an alert, not just record it — block an IP, disable an account, kill a process.

<!-- 1. Declare the command -->
<command>
  <name>firewall-drop</name>
  <executable>firewall-drop</executable>
  <timeout_allowed>yes</timeout_allowed>
</command>

<!-- 2. Bind it to a trigger -->
<active-response>
  <command>firewall-drop</command>
  <location>local</location>      <!-- run on the agent that alerted -->
  <rules_id>5712</rules_id>       <!-- SSH brute force -->
  <timeout>600</timeout>          <!-- undo after 10 minutes -->
</active-response>

Built-in Scripts

  • firewall-drop — block the source IP
  • host-deny — add to hosts.deny
  • disable-account — lock the user
  • restart-wazuh — restart the agent

Use It Carefully

  • A false positive now becomes an outage
  • Always set a timeout so blocks expire
  • Whitelist your own admin and monitoring IPs
  • Start in a test group before rolling out

MITRE ATT&CK & Compliance

Rules can be tagged. Those tags are what turn a pile of alerts into a report an auditor or a threat hunter can read.

<rule id="100010" level="10">
  <if_sid>5716</if_sid>
  <description>SSH authentication failure</description>

  <mitre>
    <id>T1110</id>              <!-- Brute Force -->
  </mitre>

  <group>authentication_failed,</group>
  <pci_dss>10.2.4,10.2.5</pci_dss>
  <gdpr>IV_35.7.d</gdpr>
  <hipaa>164.312.b</hipaa>
  <nist_800_53>AU.14,AC.7</nist_800_53>
</rule>

MITRE ATT&CK

A public catalogue of attacker techniques (T-numbers). The dashboard shows which techniques your alerts map to — and, more usefully, which ones you have no coverage for.

Compliance Frameworks

Built-in mappings for PCI DSS, GDPR, HIPAA, NIST 800-53, TSC and GPG13. Each has a ready-made dashboard, so "show me evidence for control X" is a filter, not a project.

The Indexer & Retention

What Gets Stored

  • wazuh-alerts-4.x-* — alerts, one index per day
  • wazuh-archives-4.x-* — every event, off by default
  • wazuh-states-vulnerabilities-* — current CVE state

Turning archives on is how you keep events that fired no rule. It is also how you fill a disk. Enable it deliberately, size it first.

Retention with ISM

# Index State Management policy
hot    0-7 days    fast disk, searchable
warm   7-30 days   moved, still searchable
cold   30-90 days  minimal resources
delete after 90 days

# Check what you are using
curl -k -u admin:pass \
  https://localhost:9200/_cat/indices/wazuh-alerts-*?v

Your retention window is a compliance decision first and a disk decision second. Agree it before you build.

The Dashboard — Threat Hunting

Getting Around

  • Modules — one view per capability: FIM, SCA, vulnerabilities, MITRE
  • Agents — per-endpoint drill-down
  • Discover — raw alert search, where hunting really happens
  • Management — rules, decoders, groups, config

Queries to Start With

# Everything serious in the last 24h
rule.level >= 12

# Brute force against one host
rule.groups: authentication_failed
  and agent.name: "web-01"

# Files changed outside a maintenance window
rule.groups: syscheck
  and syscheck.event: modified

# One attacker's whole footprint
data.srcip: "203.0.113.9"

# Everything mapped to a technique
rule.mitre.id: "T1110"

Hunting is mostly pivoting: start from one alert, pull the source IP or username, and ask what else that identifier touched.

The Wazuh API & RBAC

Everything the dashboard does, it does through the REST API on tcp/55000. So can your scripts.

# 1. Get a token (valid ~15 minutes by default)
TOKEN=$(curl -sk -u wazuh-wui:PASSWORD -X POST \
  "https://localhost:55000/security/user/authenticate?raw=true")

# 2. Use it
curl -sk -H "Authorization: Bearer $TOKEN" \
  "https://localhost:55000/agents?status=active&limit=5"

# List agents that stopped reporting
curl -sk -H "Authorization: Bearer $TOKEN" \
  "https://localhost:55000/agents?status=disconnected"

# Restart an agent
curl -sk -X PUT -H "Authorization: Bearer $TOKEN" \
  "https://localhost:55000/agents/001/restart"

RBAC is built on three pieces: a policy says what may be done to which resources, a role bundles policies, and a user holds roles. Give your SOC analysts read-only roles and keep agent deletion to admins.

Getting Alerts Out

  • Slack / PagerDuty — notify a human
  • TheHive — open a case per alert
  • Shuffle — run a full SOAR playbook
  • Email, or any script you write yourself
<integration>
  <name>slack</name>
  <hook_url>https://hooks.slack.com/...</hook_url>
  <level>12</level>
  <alert_format>json</alert_format>
</integration>

Set <level> high. An integration that pages on every level-3 alert gets muted within a week.

Tuning & Reducing False Positives

A fresh Wazuh install is loud. Tuning is not optional — an ignored dashboard detects nothing.

<!-- Silence a noisy rule without editing the official ruleset:
     override it at level 0 in local_rules.xml -->
<rule id="100050" level="0">
  <if_sid>5715</if_sid>
  <srcip>10.0.0.0/8</srcip>
  <description>Ignore SSH logins from the internal network</description>
</rule>

<!-- Or raise the bar for what gets stored at all -->
<alerts>
  <log_alert_level>5</log_alert_level>
</alerts>
▸ Never edit files in /var/ossec/ruleset/ — upgrades overwrite them
▸ Override in local_rules.xml using if_sid instead
▸ Exclude backup and log paths from FIM before it floods you
▸ Tune the top 5 noisiest rules each week until it is quiet
▸ Suppress by context (source IP, agent group), not by deleting rules
▸ Always wazuh-logtest before restarting the manager

Best Practices

1. Start with one agent group and a handful of log sources — expand once it is quiet
2. Configure by group via agent.conf, never box by box
3. Keep all custom work in local_rules.xml and local_decoder.xml
4. Use rule IDs 100000+ so upgrades never clobber them
5. Test every rule with wazuh-logtest before restarting
6. Decide retention from compliance requirements, then size disk to match
7. Enable FIM whodata only where you need attribution — it costs
8. Route only level 12+ to Slack or PagerDuty; hunt the rest in the dashboard
9. Give Active Response a timeout and an allowlist before enabling it
10. Version-control your rules, decoders, and ossec.conf in Git
11. Back up /var/ossec/etc/ and the agent key store
12. Treat the dashboard as a habit — review weekly, or it stops being a control
