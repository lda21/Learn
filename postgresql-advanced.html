Scope & Architecture

This is the deep dive. We assume you write SQL fluently and know what an index is. The focus is internals, performance, and operations on Postgres 17/18.

Postgres is a process-per-connection system. The postmaster supervisor forks a dedicated backend process for every client connection; shared memory and background workers tie them together.

Memory Architecture

Postgres memory splits into one big shared region and many per-backend allocations. Knowing which is which is the key to safe tuning.

AreaScopePurpose
shared_buffersSharedPostgres's own page cache (typically 25% of RAM)
wal_buffersSharedWAL records staged before flush to disk
work_memPer operationSorts & hashes; allocated per node, per backend
maintenance_work_memPer backendVACUUM, CREATE INDEX, ALTER TABLE

Critical gotcha: work_mem is not a global limit. A single query with several sorts/hashes can use many multiples of it, and every concurrent backend multiplies it again. Size it against max_connections.

OS cache matters too: pages not in shared_buffers are often still hot in the kernel page cache. effective_cache_size tells the planner how much total cache (Postgres + OS) it can assume.

MVCC: How Concurrency Works

Postgres never overwrites a row in place. Every UPDATE/DELETE creates a new tuple version and marks the old one expired. Readers never block writers, and writers never block readers.

Hidden system columns

  • xmin — the transaction ID that inserted the tuple
  • xmax — the transaction that deleted/updated it (0 if live)
  • ctid — the physical (page, offset) location

Snapshots & visibility

  • A transaction takes a snapshot of which XIDs are committed
  • A tuple is visible if its xmin committed before the snapshot and xmax did not
  • No read locks needed — visibility is computed per tuple
SELECT xmin, xmax, ctid, * FROM accounts WHERE id = 42;
-- xmin/xmax expose the version history MVCC tracks under the hood

The cost of this elegance: old versions pile up as dead tuples that VACUUM must later reclaim.

Heap Storage & Page Layout

A table (the "heap") is an array of 8 KB pages. Each page holds a header, an array of item pointers, and tuples that grow inward from the end.

TOAST

A value too big for a page (> ~2 KB) is compressed and/or sliced into a side TOAST table. Large text/jsonb/bytea live there transparently — reading them is extra I/O.

HOT updates

Heap-Only Tuple updates: if no indexed column changes and the new version fits on the same page, Postgres chains it without touching any index. Far cheaper — design tables to keep updates HOT.

A lower fillfactor (e.g. 90) leaves room on each page for future HOT updates on hot-write tables.

Dead Tuples, Bloat & VACUUM

Because MVCC leaves dead versions behind, tables and indexes accumulate bloat — space occupied by tuples no transaction can see anymore.

VACUUM

  • Marks dead tuples' space reusable in place
  • Updates the visibility map & free space map
  • Does not return disk to the OS — but online & non-blocking

VACUUM FULL

  • Rewrites the whole table compactly
  • Returns space to the OS
  • Takes an ACCESS EXCLUSIVE lock — blocks all access

The visibility map tracks pages where every tuple is visible to all transactions. It powers index-only scans and lets VACUUM skip all-visible pages.

For online bloat removal without a heavy lock, prefer pg_repack or VACUUM FULL during a maintenance window. Monitor bloat with pgstattuple.

Autovacuum Tuning

Autovacuum runs VACUUM and ANALYZE automatically. A table is vacuumed when dead tuples exceed a threshold + scale factor of its size.

-- Trigger ~ threshold + scale_factor * reltuples
-- Defaults: threshold = 50, scale_factor = 0.2 (20% of the table)
-- On a 100M-row table, 20% = 20M dead rows before it fires — far too lax.

ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,   -- vacuum at 2% dead
  autovacuum_vacuum_cost_delay   = 2ms,    -- run more aggressively
  autovacuum_vacuum_insert_scale_factor = 0.05
);

When it falls behind

  • Long-running transactions hold back the "oldest visible" XID
  • Cost-based delay throttles it too hard under heavy write load
  • Too few autovacuum_max_workers for many big tables

Tune per-table

  • Lower scale factors on huge, churny tables
  • Raise maintenance_work_mem for faster index cleanup
  • Watch pg_stat_user_tables.n_dead_tup and last_autovacuum

XID Wraparound & Freezing

Transaction IDs are 32-bit and wrap around. Postgres treats XIDs as a circular space ~2 billion wide. Old tuples must be frozen (marked "visible to everyone, forever") before their XID falls out of range.

The horizon

If unfrozen XIDs approach the 2-billion limit, Postgres refuses new writes to protect data — a database-down emergency.

Aggressive vacuum

Once a table's age exceeds autovacuum_freeze_max_age (default 200M), an anti-wraparound vacuum is forced — even on idle tables.

Freezing

VACUUM rewrites old tuples' visibility info so their XIDs can be recycled. Postgres 17+ tracks this more efficiently per page.

Monitor it

Watch age(datfrozenxid) per database; alert well before autovacuum_freeze_max_age.

SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database ORDER BY xid_age DESC;

The Query Planner

Postgres uses a cost-based optimizer. It enumerates candidate plans, estimates each one's cost in abstract units, and picks the cheapest. Costs come from statistics, not from running the query.

Statistics

  • ANALYZE samples rows into pg_statistic
  • Tracks n_distinct, most-common values, histograms, null fraction
  • Estimates row counts (cardinality) for each operation

Cost knobs

  • seq_page_cost = 1.0, random_page_cost = 4.0 (lower on SSD)
  • cpu_tuple_cost, cpu_index_tuple_cost
  • effective_cache_size biases toward index plans

Bad estimates = bad plans. Most "Postgres is slow" problems trace back to stale statistics or estimates that miss correlated columns — not the engine itself.

Reading EXPLAIN (ANALYZE, BUFFERS)

EXPLAIN shows the plan; ANALYZE actually runs it and reports real timing and rows; BUFFERS exposes the I/O. Read it inside-out, bottom-up.

EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT * FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= now() - interval '7 days';

 Hash Join  (cost=210.5..980.3 rows=1200 width=84)
             (actual time=2.1..15.4 rows=48000 loops=1)
   Buffers: shared hit=820 read=1340
   ->  Seq Scan on orders o  (rows=1200)  (actual rows=48000)   <-- 40x off!
         Filter: (created_at >= ...)
   ->  Hash  ->  Seq Scan on customers c

What to look for: a large gap between estimated and actual rows (here 1200 vs 48000) signals stale stats or a missing index. High read buffers mean cache misses. Watch for unexpected Seq Scans and rows growing as you go up the tree.

Scan Types

ScanWhen chosenCost profile
Seq ScanReading a large fraction of the tableSequential I/O; great for full reads
Index ScanHighly selective predicateRandom I/O to heap per match
Index-Only ScanAll needed columns in the index & page all-visibleNo heap visit — fastest
Bitmap Heap ScanMedium selectivity; combine multiple indexesBuilds a bitmap, then reads heap in page order

A Seq Scan is not always bad. If a query touches 40% of rows, scanning sequentially beats millions of random index lookups. The planner picks based on estimated selectivity.

Bitmap scans bridge the gap: they collect matching tuple locations from one or more indexes into a bitmap, sort by physical page, then fetch the heap once per page — turning random I/O into near-sequential.

Join Algorithms

Nested Loop

For each outer row, probe the inner side. Wins when one side is tiny or the inner has a usable index. O(n×m) without an index.

Hash Join

Build a hash table on the smaller side, probe with the larger. Best for big, unsorted, equality joins. Needs work_mem; spills to disk if it overflows.

Merge Join

Both inputs sorted on the join key, then merged. Great when inputs are already ordered (e.g. by an index).

Planner picks

Selection is cost-driven by estimated row counts. A misestimate can pick a Nested Loop over millions of rows — a classic disaster.

-- A Nested Loop with huge "actual rows" on the inner side is a red flag:
-> Nested Loop (actual rows=2000000 loops=4000)   -- should have been a Hash Join

B-tree Indexes Deep Dive

B-tree is the default and the workhorse: balanced, sorted, supporting =, range, ORDER BY, and IN. Understanding multicolumn ordering is where engineers win.

Column order rule

In (a, b, c), the index helps queries on a, a,b, and a,b,c — a left-prefix. It cannot efficiently serve a query filtering only on b. Put equality columns first, range columns last.

INCLUDE columns

Covering indexes add non-key payload columns so an index-only scan can return them without a heap visit — without bloating the tree's search keys.

-- Equality on customer_id, range on created_at, covering total:
CREATE INDEX idx_orders ON orders (customer_id, created_at) INCLUDE (total);

SELECT total FROM orders
WHERE customer_id = 7 AND created_at >= '2026-01-01';   -- index-only scan

GIN

Inverts each contained element to a posting list. The right choice for jsonb containment and full-text. Larger and slower to update than B-tree.

BRIN

Stores min/max summaries per block range. Tiny on disk, but only effective when rows are physically ordered by the indexed column.

Partial, Expression & Maintenance

-- Partial: index only the rows you actually query — smaller, faster
CREATE INDEX idx_active ON users (last_login) WHERE status = 'active';

-- Expression: match the exact expression used in WHERE
CREATE INDEX idx_lower_email ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.com';   -- uses the index

Index bloat & rebuilds

  • Indexes bloat from churn just like heaps
  • REINDEX CONCURRENTLY rebuilds without an exclusive lock
  • Find unused indexes via pg_stat_user_indexes (idx_scan = 0)

Build without blocking

  • CREATE INDEX CONCURRENTLY avoids locking writes
  • Slower & can leave an invalid index if it fails — drop & retry
  • Every index is write overhead — audit and prune

Extended Statistics

The planner assumes columns are independent. When they're correlated, row estimates collapse and plans go wrong. CREATE STATISTICS teaches the planner about the relationship.

-- city and state are correlated; the planner under-estimates the combo
CREATE STATISTICS s_city_state (dependencies, ndistinct, mcv)
  ON city, state FROM addresses;
ANALYZE addresses;

dependencies

Captures functional dependencies (zip → city) so combined-predicate estimates stop multiplying down to near-zero.

ndistinct

Tracks distinct counts for groups of columns — vital for GROUP BY on multiple columns.

mcv

Most-common combinations of values, improving estimates for skewed multi-column filters.

n_distinct override

You can also set ALTER TABLE ... ALTER COLUMN ... SET (n_distinct = ...) when ANALYZE samples poorly.

Table Partitioning

Declarative partitioning splits one logical table into physical child tables by RANGE, LIST, or HASH. The win comes from partition pruning, not raw partition count.

CREATE TABLE events (id bigint, ts timestamptz, payload jsonb)
  PARTITION BY RANGE (ts);

CREATE TABLE events_2026_06 PARTITION OF events
  FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

-- Planner prunes to a single partition using the ts predicate:
EXPLAIN SELECT * FROM events WHERE ts >= '2026-06-10';

Why it helps

  • Pruning skips irrelevant partitions entirely
  • Drop old data instantly via DROP TABLE on a partition
  • Smaller per-partition indexes & faster vacuum

Watch out

  • Queries without the partition key scan all partitions
  • Enable partition-wise joins/aggregates for big gains
  • Too many partitions inflates planning time

Locking & Concurrency

Readers and writers rarely conflict thanks to MVCC, but writers contend on the same rows, and DDL takes heavy table locks. Knowing the lock modes prevents production stalls.

Row vs table locks

  • SELECT ... FOR UPDATE locks rows for a write you're about to do
  • FOR NO KEY UPDATE / FOR SHARE are lighter variants
  • DDL like ALTER TABLE grabs ACCESS EXCLUSIVE — blocks everything

Deadlocks

  • Two txns lock rows in opposite order
  • Postgres detects the cycle and aborts one
  • Fix: lock rows in a consistent order; keep txns short
-- Find what's blocking what, right now:
SELECT pid, mode, relation::regclass, granted FROM pg_locks
JOIN pg_stat_activity USING (pid) WHERE NOT granted;

Isolation Levels in Practice

LevelPreventsBehavior in Postgres
Read Committed (default)Dirty readsEach statement sees a fresh snapshot; non-repeatable reads possible
Repeatable Read+ non-repeatable & phantom readsOne snapshot for the whole txn; may abort with a serialization error
Serializable (SSI)All anomaliesActs as if txns ran one at a time; aborts on dangerous patterns

Postgres's Repeatable Read already blocks phantom reads (stronger than the SQL standard requires). Serializable Snapshot Isolation (SSI) adds predicate-level conflict tracking with no extra locks.

Trade-off: RR and Serializable can throw could not serialize access errors — your app must retry the whole transaction. Use them for read-modify-write logic where correctness beats a retry loop.

Connection Management & Pooling

Each connection is a full OS process with its own memory. Thousands of connections crush a server even when mostly idle — pooling is not optional at scale.

Why pool

  • Backends cost RAM & context-switching even when idle
  • max_connections in the low hundreds is healthy, not thousands
  • Pool reuses a small set of real backends

PgBouncer modes

  • Transaction pooling: backend returned after each txn — highest reuse
  • Beware: session-level features (prepared statements, SET) need care
  • Session mode is safe but reuses less

Replication & High Availability

Replication ships the WAL stream to standbys. This powers read scaling, failover, and zero-downtime upgrades.

Physical (streaming)

  • Byte-for-byte WAL replay to a standby
  • Replication slots stop the primary recycling WAL a lagging standby still needs
  • Standbys serve read-only queries (hot standby)

Logical

  • Decodes WAL into row-level changes (publications/subscriptions)
  • Selective tables, cross-version, different schemas
  • Ideal for upgrades & data integration

Sync vs async: synchronous_commit with a sync standby guarantees no data loss on failover but adds commit latency. Async is faster but can lose the last few transactions. Failover promotes a standby; tools like Patroni automate it.

Performance Tuning Workflow

Don't guess — measure. pg_stat_statements is the single most valuable tool for finding where time actually goes.

-- Top queries by total time across the whole server:
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

pg_stat_statements

Aggregates normalized queries by total/mean time, calls, and rows. Start here, optimize the top of the list.

pg_stat_activity

Live view of running queries, their state, and wait_event — what each backend is blocked on right now.

Wait events

Lock waits, I/O waits, WAL waits — tell you whether you're CPU, I/O, or contention bound.

EXPLAIN the worst

Take the top offenders and run EXPLAIN (ANALYZE, BUFFERS) to find the bad node.

Server Configuration Tuning

A handful of GUCs drive most performance. Start from sane baselines for your RAM and storage, then tune from measurements.

SettingTypicalEffect
shared_buffers~25% RAMPostgres page cache size
effective_cache_size~50-75% RAMPlanner's view of total cache → favors indexes
work_memPer-op, by concurrencyBigger sorts/hashes in memory, avoid disk spills
random_page_cost1.1 on SSDLower makes index scans more attractive
max_wal_sizeWorkload-dependentControls checkpoint frequency

Parallelism: max_parallel_workers_per_gather lets large scans, joins, and aggregates use multiple cores. Raise it for analytical workloads; the planner only parallelizes when the estimated cost justifies the worker startup overhead.

Best Practices

1 EXPLAIN before you optimize — verify the bottleneck instead of guessing
2 Keep statistics fresh; add extended statistics for correlated columns
3 Practice index hygiene — cover real queries, drop unused indexes
4 Tune autovacuum per table; never let it fall behind on churny tables
5 Monitor bloat and XID wraparound proactively with alerts
6 Design updates to stay HOT; tune fillfactor on hot-write tables
7 Batch writes and keep transactions short to limit dead tuples & lock time
8 Pick the right isolation level and add retry logic for serialization errors
9 Put a connection pooler (PgBouncer) in front; keep max_connections modest
10 Use replication slots for standbys, but monitor lag so WAL doesn't pile up
