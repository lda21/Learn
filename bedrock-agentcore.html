Why AgentCore?

The Production Gap

  • Building an agent in a notebook is easy
  • Running one in production is not
  • Sessions need isolation, identity, memory
  • Tools need auth, discovery, governance
  • Ops need tracing, debugging, scale

What AgentCore Provides

  • Serverless hosting for any agent framework
  • Any LLM (Bedrock, OpenAI, Gemini, self-hosted)
  • Memory, identity, tools, observability as primitives
  • Compose services independently — no lock-in
  • GA October 2025

AgentCore is the infrastructure layer for agents — the equivalent of EC2/Lambda for code.

The Seven Services

Runtime

Serverless agent hosting on isolated microVMs. Up to 8-hour sessions.

Memory

Short-term session context + long-term durable memory across sessions.

Identity

OAuth + IAM auth for agents to act on behalf of users or themselves.

Gateway

Turn APIs, Lambdas, and MCP servers into agent-discoverable tools.

Code Interpreter

Sandboxed Python/JS/TS execution for agent-written code.

Browser

Managed Chromium for web automation, scraping, and form-fill tasks.

Plus Observability — OpenTelemetry traces, metrics, and CloudWatch GenAI dashboards across all six services.

Runtime: Serverless Hosting

What It Is

  • Purpose-built serverless runtime for agents
  • Each session in its own microVM (Firecracker)
  • Isolated CPU, memory, filesystem per session
  • Sessions up to 8 hours long
  • Scales to zero, billed per session

Why MicroVMs?

  • Hard isolation between user sessions
  • Untrusted code (Code Interpreter) is contained
  • Stateful: long reasoning loops keep working memory
  • No shared kernel attack surface
  • Same primitive Lambda uses, with longer leases

Key insight: agent sessions are stateful and long-lived — Lambda's 15-minute cap can't host them. Runtime is built for this.

Runtime: Framework & Model Agnostic

Frameworks Supported

  • Strands Agents — AWS-native
  • LangGraph — LangChain stateful agents
  • CrewAI — multi-agent crews
  • LlamaIndex — RAG-first agents
  • Or any custom Python / TypeScript

Models Supported

  • Bedrock: Claude, Nova, Llama, Mistral
  • OpenAI (GPT family) via API key
  • Google Gemini via API key
  • Self-hosted: any HTTP-callable model
  • Bring your own inference endpoint

BedrockAgentCoreApp is just an entrypoint wrapper — your agent code stays the same.

Runtime: Deploy in Three Steps

# 1. Wrap your agent with the AgentCore entrypoint
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from strands import Agent  # or LangGraph, CrewAI, etc.

app = BedrockAgentCoreApp()
agent = Agent(model="anthropic.claude-sonnet-4-5-v1:0")

@app.entrypoint
def invoke(payload):
    user_msg = payload["prompt"]
    response = agent(user_msg)
    return {"result": response.message}

if __name__ == "__main__":
    app.run()

# 2. Configure (auto-builds Dockerfile + IAM role)
$ agentcore configure --entrypoint agent.py

# 3. Deploy to AWS
$ agentcore launch
$ agentcore invoke '{"prompt": "Plan my trip to Tokyo"}'

No Dockerfile, no Kubernetes, no Terraform. The CLI builds the container, pushes to ECR, and wires up the runtime.

Memory: Short and Long Term

Short-Term Memory

  • The current session's conversation history
  • Raw turns: user message + agent response
  • Auto-managed within a session
  • Available immediately, no extraction needed
  • Scoped by actorId + sessionId

Long-Term Memory

  • Persists across sessions and weeks
  • AgentCore extracts and consolidates from raw events
  • Stored in namespaces per user / agent / topic
  • Retrieved by semantic similarity at query time
  • Built on CreateMemory + RetrieveMemoryRecords APIs

A session ends. The user comes back tomorrow. Long-term memory remembers they're vegan and prefer aisle seats — without you wiring up a vector DB.

Memory: Built-In Strategies

Semantic Memory

Extracts and stores facts the user mentioned, indexed for retrieval by meaning.

Summary Memory

Rolling summaries of past sessions, so the agent has context without replaying every turn.

User Preferences

Likes, dislikes, communication style. Auto-extracted from conversation patterns.

Self-Managed

Bring your own extraction + consolidation pipeline. AgentCore stores, you decide what.

# Retrieve relevant long-term memory at the start of a turn
records = client.retrieve_memory_records(
    memoryId="mem-prod-123",
    namespace=f"users/{user_id}/preferences",
    searchCriteria={"searchQuery": user_msg, "topK": 5}
)
context = "\n".join(r["content"]["text"] for r in records["memoryRecordSummaries"])

Identity: Agents Need Auth Too

The Problem

  • An agent needs to call your APIs
  • And third-party APIs: Slack, GitHub, Salesforce
  • On behalf of specific users
  • Without storing raw user passwords
  • With auditable, scoped permissions

What Identity Provides

  • OAuth 2.0 / OIDC integration with Cognito, Okta, Entra, Auth0
  • IAM authorization for AWS resources
  • Encrypted vault for refresh tokens
  • Identity-aware authorization policies
  • Workload identity for agent-to-agent calls

No more env vars full of long-lived API keys. Tokens are minted per-call, scoped, and revocable.

Inbound (who calls the agent)

  • JWT validated against your IdP
  • Identity flows into the agent context
  • Used to scope memory and tool access

Outbound (what the agent calls)

  • 3LO — on behalf of user (user consents once, vault stores refresh)
  • 2LO — agent's own machine identity
  • Tokens minted just-in-time per tool call

Gateway: Tools as MCP

What Gateway Does

  • Single secure endpoint for all agent tools
  • Speaks the Model Context Protocol (MCP)
  • Wraps existing APIs and Lambda functions as tools
  • Connects to existing MCP servers
  • Enforces IAM and OAuth on every tool call

Tool Sources

  • OpenAPI / Smithy — auto-generated tool schemas from API specs
  • Lambda — functions become tools directly
  • MCP servers — reuse the open ecosystem
  • Semantic tool search at scale (1000s of tools)

Without Gateway, every framework re-implements tool wiring. With Gateway, you ship one MCP endpoint and any agent can use it.

Gateway: Lambda → Tool

# 1. Create a Gateway
gw = client.create_gateway(
    name="weather-tools",
    protocolType="MCP",
    authorizerType="CUSTOM_JWT",
    authorizerConfiguration={
        "customJWTAuthorizer": {
            "discoveryUrl": "https://cognito-idp.us-east-1.amazonaws.com/POOL/.well-known/openid-configuration",
            "allowedClients": ["client-id-123"]
        }
    }
)

# 2. Attach a Lambda target (becomes a discoverable MCP tool)
target = client.create_gateway_target(
    gatewayIdentifier=gw["gatewayId"],
    name="get-forecast",
    targetConfiguration={
        "mcp": {"lambda": {"lambdaArn": "arn:aws:lambda:...:fn:weather"}}
    }
)

# 3. Any MCP-aware agent now sees "get-forecast" as a tool
# Strands, LangGraph, Claude Desktop — all just point at the gateway URL

One Lambda, many agents. Add a target, every connected agent discovers the new tool automatically.

Built-In Tool: Code Interpreter

What It Does

  • Sandboxed execution of Python, JS, TS
  • Each session in its own microVM
  • Pre-installed: pandas, numpy, matplotlib, requests
  • File upload & download in/out of the sandbox
  • No network egress by default

Why Use It

  • Agent does math without hallucinating arithmetic
  • Generate charts and CSVs from user prompts
  • Parse uploaded PDFs / spreadsheets
  • Run untrusted user code safely
  • Replaces fragile eval() tools
from bedrock_agentcore.tools.code_interpreter import code_session

with code_session("us-west-2") as ci:
    result = ci.invoke("executeCode", {
        "code": "import pandas as pd; df = pd.read_csv('sales.csv'); print(df.describe())",
        "language": "python",
        "clearContext": False
    })

Built-In Tool: Browser

Managed Chromium

  • Headful or headless Chromium in a microVM
  • Speaks CDP (Chrome DevTools Protocol)
  • Compatible with Playwright, Puppeteer
  • Live view URL for debugging
  • Per-session isolation — no cross-user cookie leakage

What Agents Do With It

  • Fill out forms on legacy web apps without APIs
  • Scrape behind login walls (with user OAuth)
  • Take screenshots for vision-model analysis
  • Run end-to-end checkout / booking flows
  • Reproduce user-reported bugs
from bedrock_agentcore.tools.browser_client import browser_session

with browser_session("us-west-2") as browser:
    cdp_url = browser.get_cdp_url()
    # Drive with Playwright
    page = await playwright_browser.connect_over_cdp(cdp_url)
    await page.goto("https://internal-app.corp/")

Observability

OpenTelemetry Native

  • Spans for every model call, tool call, memory op
  • Standard OTel exporters — ship to any backend
  • Auto-instrumented when you enable it on Runtime
  • GenAI semantic conventions for prompts and tokens

CloudWatch GenAI

  • Pre-built dashboards: latency, tokens, errors
  • Per-session and per-agent breakdowns
  • Trace explorer with prompt / response payloads
  • Alarms on cost, error rate, p99 latency
# Enable observability on a runtime — that's it
client.update_agent_runtime(
    agentRuntimeId="rt-prod",
    observabilityConfiguration={"traceLevel": "ALL"}
)
# Spans now flow to CloudWatch + your OTel collector

When the agent does something weird, you get the full trace: which tool, which prompt, which tokens.

Best Practices

1. Pick services a la carte — don't adopt all seven on day one
2. Wire identity first — refactoring auth later is painful
3. Use namespaces in Memory like users/{id}/prefs for clean isolation
4. Put tools behind Gateway even if you have one agent — you'll add more
5. Always run untrusted code in Code Interpreter, never inside the runtime
6. Set explicit session timeouts — long agents are expensive when looping
7. Sample observability traces at high volume; full traces on errors
8. Version your prompts and eval them in CI — AgentCore won't do that for you
9. Keep agent code thin — push tools to Gateway, push state to Memory
10. Monitor cost per session, not per request — sessions are the unit of work
