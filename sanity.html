Sanity GROQ Headless CMS Portable Text

Structured content, not pages

Page CMS habit

  • Editors compose a page as HTML or blocks
  • Presentation is baked into the record
  • Reuse means copy-paste or fragile embeds
  • A new channel (app, email, kiosk) needs a rewrite

Sanity’s bet

  • Model facts: post, product, author, SEO
  • Store JSON in the Content Lake
  • Query the shape the frontend needs with GROQ
  • Render later — web, app, or preview iframe

The Studio is the editor UI. The Lake is the API. Your app is the presentation layer.

The three pieces

Studio
schema + editor UI
→
Content Lake
JSON + real-time API
→
Frontend
GROQ + client
  • Studio is configured in code (sanity.config.ts). Schemas live there, not as database constraints.
  • Content Lake stores any valid JSON document. Drafts, published, and releases are perspectives on the same ids.
  • Your app fetches with @sanity/client or next-sanity, then renders Portable Text and images.

Content Lake

JSON documents

Every record is an object with _id, _type, _rev, _createdAt, _updatedAt.

Schema is UI, not a lock

Studio schemas describe what editors may author. The Lake will store JSON that no schema covers.

Query, don’t scrape

GROQ filters, joins, and projects at the API. Frontends receive only the fields they asked for.

Perspectives

published for production. drafts (and releases) for preview. Same query, different state.

Studio configuration

defineConfig

Required: projectId and dataset. Typical plugins: structureTool() (the desk), visionTool() (GROQ playground), presentationTool() (live preview).

Put types on schema.types. Keep the array in schemaTypes.ts and import it.

import {defineConfig} from 'sanity'
import {structureTool} from 'sanity/structure'
import {schemaTypes} from './schemaTypes'

export default defineConfig({
  projectId: 'abc123',
  dataset: 'production',
  plugins: [structureTool()],
  schema: { types: schemaTypes },
})

Schema definition

Typed helpers

  • defineType wraps a type (document or object)
  • defineField wraps each field for autocomplete
  • Every field needs name (JSON key) and type
  • validation is a Rule builder: Rule.required()
import {defineField, defineType} from 'sanity'

export const postType = defineType({
  name: 'post',
  title: 'Post',
  type: 'document',
  fields: [
    defineField({
      name: 'title',
      type: 'string',
      validation: (rule) => rule.required(),
    }),
    defineField({
      name: 'slug',
      type: 'slug',
      options: {source: 'title'},
    }),
  ],
})

Document types

A document is what editors create in the Structure tool. Only documents get an id, timestamps, and a revision, and only documents can be referenced or fetched by id.

Use type: 'document' for

  • Standalone content: post, page, product, author
  • Anything that needs its own Studio list item
  • Anything other documents will reference

Stored shape

{
  "_id": "post-42",
  "_type": "post",
  "_rev": "abc",
  "title": "Hello",
  "slug": { "current": "hello" }
}

Object types vs documents

DocumentObject
Standalone in StudioYes — listed and creatableNo — lives inside a parent
Has _id / _revYesOnly _type + _key in arrays
Can be referencedYes (_ref)Embed the fields instead
Typical usepost, author, categoryseo, cta, address, portable-text block

Never put a document type on a field. Embed an object, or point at a document with type: 'reference'.

References vs embedded objects

Reference

defineField({
  name: 'author',
  type: 'reference',
  to: [{type: 'author'}],
})

Stores {_ref, _type: 'reference'}. One author, many posts. GROQ follows it with ->.

Embedded object

defineField({
  name: 'seo',
  type: 'seo', // hoisted object type
})

Fields live on the parent document. Use when the data is not shared and has no independent lifecycle.

GROQ is a pipeline

*
all documents
→
[filter]
keep matching
→
{projection}
reshape JSON
→
| order / slice
sort and page

GROQ (Graph-Relational Object Queries) runs in the Content Lake. You describe which documents, then which fields, then joins and computed keys. The frontend receives the finished shape.

Use it from client.fetch, the HTTP /query endpoint, Vision in Studio, webhooks, and Functions. Vision is the playground: paste a query, inspect JSON, then copy it into the app.

Filters and projections

Filter

*[_type == "post"
  && defined(slug.current)
  && publishedAt <= now()]

* is the dataset. Square brackets keep documents. Combine with && / ||.

Project

*[_type == "post"]{
  _id,
  title,
  "slug": slug.current,
  "excerpt": pt::text(body)[0...160]
}

Curly braces pick and rename fields. Quoted keys are computed.

Joins, order, perspectives

*[_type == "post"] | order(publishedAt desc) [0...12] {
  title,
  "slug": slug.current,
  "author": author->{name, "slug": slug.current},
  categories[]->{title, "slug": slug.current}
}

Dereference

-> follows a reference. author->name is one field; author->{...} is a nested object. Arrays: categories[]->.

Perspective

Client default published + useCdn: true for production. Override to drafts (CDN off) in preview. Same GROQ, different documents.

Sanity Client

@sanity/client

Framework-agnostic. createClient + fetch(query, params). Pin apiVersion to a date. Token only when you need drafts or writes.

import {createClient} from '@sanity/client'

export const client = createClient({
  projectId: process.env.SANITY_PROJECT_ID,
  dataset: 'production',
  apiVersion: '2025-02-19',
  useCdn: true,
  perspective: 'published',
})

const posts = await client.fetch(
  `*[_type == "post"]{title, "slug": slug.current}`
)

Next.js with next-sanity

What the kit adds

  • createClient from next-sanity (same options)
  • defineLive → sanityFetch + SanityLive
  • Draft Mode routes for Presentation
  • stega.studioUrl so overlays know where Studio lives

Public env: project id + dataset. Server-only: SANITY_API_READ_TOKEN (Viewer) for drafts.

const {data: post} = await sanityFetch({
  query: `*[_type == "post"
    && slug.current == $slug][0]{
    title, body
  }`,
  params: {slug},
  perspective: 'published',
  stega: false,
})

Prefer sanityFetch over raw client.fetch so cache, perspective, and stega stay consistent.

Live preview

Live Content API

defineLive({ client, serverToken, browserToken }) wires the query layer to fine-grained mutations. SanityLive in the app tree listens; when an editor types, cached pages re-render.

Two modes, one query

  • Published: CDN on, stega off, no token in the browser
  • Draft / Presentation: perspective from cookies, stega on, read token only while Draft Mode is enabled

Resolve perspective outside cache boundaries, then pass it into sanityFetch.

Portable Text is JSON

Schema

{
  name: 'body',
  type: 'array',
  of: [
    {type: 'block'},
    {type: 'image'},
  ],
}

Rich text is an array of blocks, not HTML. block is paragraphs, lists, marks. Custom objects sit beside blocks.

Stored block

  • _type: 'block' + children (spans)
  • Decorators (strong) live on the span’s marks
  • Annotations (links) are objects in markDefs
  • Custom blocks keep their own fields + _key

Rendering Portable Text

React serializer

import {PortableText} from '@portabletext/react'

<PortableText
  value={post.body}
  components={{
    types: {image: ImageBlock},
    marks: {link: LinkMark},
    block: {h2: H2},
  }}
/>

Query the extras

Default body is not enough for annotations that reference documents. Project them:

body[]{
  ...,
  markDefs[]{
    ...,
    _type == "internalLink" => {
      "href": "/" + @.reference->slug.current
    }
  }
}

Presentation is a map from _type to components. Images usually go through @sanity/image-url.

Practices that hold

1 Model reusable facts as documents; nest one-off shape as objects.
2 Project in GROQ. Do not over-fetch and reshape in the app.
3 Pin apiVersion. Default to published + CDN in production.
4 Keep Presentation resolve URLs in sync with real App Router paths.
5 Viewer token for drafts only; never ship a write token to the browser.
6 Reuse Portable Text projections (especially markDefs) across page queries.

What this course leaves out

Out of scope here

  • Custom Studio plugins from scratch (new tools, input components as packages)
  • Multi-workspace enterprise SSO (custom auth providers, org-wide login)

You will see defineConfig plugins used, not authored. Workspaces exist in config; we do not design SSO across them.
