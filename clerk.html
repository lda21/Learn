What is Clerk?

  • A complete authentication and user management platform — auth, sessions, and a hosted user database in one
  • Ships prebuilt, customizable UI components (<SignIn />, <UserButton />) so you don't build login screens by hand
  • Handles the hard parts: passwords, OAuth, MFA, passkeys, magic links, sessions, and JWTs
  • Built-in Organizations for multi-tenant B2B apps — teams, roles, permissions, and enterprise SSO
  • SDKs for Next.js, React, Remix, Astro, Expo, Vue, JavaScript, plus backend SDKs for Node, Python, Go, and Ruby
# The whole login screen in one line of JSX

  return <SignIn />;   // email, password, OAuth, MFA, passkeys — all included
}

Frontend API

Clerk-hosted endpoint the browser SDK talks to for sign-in, sign-up, and session management. Served from your domain via DNS (e.g. clerk.yourapp.com).

Backend API

Server-side REST API for managing users, organizations, and sessions. Called via secret key with the backend SDKs.

Session Tokens

Short-lived JWTs (default 60s) stored in a cookie, refreshed automatically. Your backend verifies them statelessly.

Clerk Dashboard

Configure auth strategies, social providers, MFA, branding, and organizations — no code deploy needed.

Core Concepts

The Object Model

  • User — a person, with emails, phones, and external accounts
  • Session — an active sign-in on a device
  • Client — a browser/device that may hold multiple sessions
  • Organization — a team/company a user belongs to
  • JWT / Claims — the verified token your API trusts

Keys

# .env.local — two keys
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...

# Publishable key  -> safe in the browser
# Secret key       -> server only, never ship

Clerk distinguishes instances: a development instance (test keys, on a shared domain) and a production instance (live keys, your own domain with proper DNS).

Authentication Strategies

Identifiers

  • Email address — the default
  • Phone number — SMS-based
  • Username — classic handle

Verification

  • Password — with breach & strength checks
  • Email link — passwordless magic link
  • Email / SMS code — one-time passcode (OTP)
  • Passkeys — WebAuthn, phishing-resistant

All of these are toggles in the Clerk Dashboard — flip on "Email code" and your <SignIn /> instantly offers passwordless OTP. No redeploy.

Passwordless flows (magic links + OTP) reduce password reuse and support burden, while passkeys eliminate phishing entirely.

Multi-Factor Auth & Passkeys

Authenticator (TOTP)

Time-based codes from Google Authenticator, Authy, 1Password. The most common second factor.

SMS Code

One-time code sent to a verified phone number as a second factor.

Backup Codes

Single-use recovery codes generated when MFA is enabled, for when a device is lost.

Passkeys (WebAuthn)

Biometric / hardware login that is phishing-resistant. Can act as a primary factor or a second factor.

// Let a user register a passkey from your custom UI
import { useUser } from '@clerk/clerk-react';

const { user } = useUser();
await user?.createPasskey();   // browser prompts for Face ID / fingerprint / security key

Enable MFA in the dashboard and the prebuilt components handle enrollment and challenge flows automatically.

Client-Side Hooks

import { useUser, useAuth, useSession, useClerk } from '@clerk/nextjs';

function Profile() {
  // useUser — the loaded User object (reactive)
  const { isLoaded, isSignedIn, user } = useUser();

  // useAuth — lightweight auth state + token getter
  const { userId, sessionId, orgId, getToken, signOut } = useAuth();

  if (!isLoaded) return null;
  if (!isSignedIn) return <p>Sign in to continue</p>;

  return (
    <div>
      <p>Hello {user.firstName} ({user.primaryEmailAddress?.emailAddress})</p>
      <button onClick={() => signOut()}>Sign out</button>
    </div>
  );
}
      
// Call your own API with a verified token
const { getToken } = useAuth();
const token = await getToken();              // default session JWT
const res = await fetch('/api/secure', {
  headers: { Authorization: `Bearer ${token}` },
});

Sessions & JWTs

How sessions work

  • Sign-in creates a session tied to the client
  • Clerk issues a short-lived JWT (~60s) in a cookie
  • The SDK auto-refreshes it in the background
  • Your backend verifies the JWT statelessly — no DB lookup

JWT Templates

Shape custom claims for third parties (Supabase, Hasura, Firebase) so they trust Clerk-issued tokens.

{
  "user_id": "{{user.id}}",
  "email": "{{user.primary_email_address}}",
  "org_role": "{{org.role}}"
}
          
// Get a token shaped by a named JWT template
const token = await getToken({ template: 'supabase' });
// Now Supabase RLS can read claims like auth.jwt() ->> 'user_id'

Server-Side Auth

// Next.js App Router — read auth in a Server Component or Route Handler
import { auth, currentUser } from '@clerk/nextjs/server';

export default async function Dashboard() {
  const { userId, orgId, redirectToSignIn } = await auth();
  if (!userId) return redirectToSignIn();

  const user = await currentUser();   // full User object, server-side
  return <h1>Welcome {user?.firstName}</h1>;
}
      
// Route Handler — protect an API and enforce a permission
import { auth } from '@clerk/nextjs/server';

export async function POST() {
  const { userId } = await auth.protect({ permission: 'org:invoices:create' });
  // auth.protect() throws a 404/redirect if the check fails
  return Response.json({ ok: true, userId });
}
      
// Manage users from the server with the Backend SDK

const client = await clerkClient();
await client.users.updateUser(userId, { publicMetadata: { plan: 'pro' } });

Middleware & Route Protection

// middleware.ts — protect routes by pattern
import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server';

const isPublicRoute = createRouteMatcher(['/', '/sign-in(.*)', '/sign-up(.*)']);
const isAdminRoute  = createRouteMatcher(['/admin(.*)']);

export default clerkMiddleware(async (auth, req) => {
  // Anything not public requires a signed-in user
  if (!isPublicRoute(req)) {
    await auth.protect();
  }
  // Admin area additionally requires a role
  if (isAdminRoute(req)) {
    await auth.protect({ role: 'org:admin' });
  }
});

export const config = {
  matcher: ['/((?!_next|.*\\..*).*)', '/(api|trpc)(.*)'],
};

Middleware runs at the edge before your pages render, so unauthorized users are redirected before any protected code executes.

User & Session Metadata

Attach your own data to users and orgs without a separate database table. Three visibility scopes:

publicMetadata

Readable on the frontend, writable only from the backend. Great for plan tier, roles, flags.

privateMetadata

Backend-only, never exposed to the client. For Stripe customer IDs, internal notes.

unsafeMetadata

Writable from the frontend by the user. For low-stakes preferences set during onboarding.

Session claims

Promote publicMetadata into the JWT so checks are instant — no API call.

// Set on the server; read instantly from the session token
await client.users.updateUserMetadata(userId, {
  publicMetadata: { plan: 'pro', onboarded: true },
});
const { sessionClaims } = await auth();   // sessionClaims.metadata.plan === 'pro'

  name: 'Acme Inc', createdBy: userId,

  organizationId: org.id, emailAddress: 'teammate@acme.com', role: 'org:member',

Roles & Permissions (RBAC)

Roles

  • Default org:admin and org:member
  • Define custom roles (e.g. org:billing)
  • Each member holds exactly one role per org

Permissions

  • Granular, e.g. org:invoices:create
  • Assigned to roles in the dashboard
  • Checked on client and server
// Server: enforce a permission
const { has } = await auth();
if (!has({ permission: 'org:invoices:create' })) {
  return new Response('Forbidden', { status: 403 });
}

// Client: conditionally render
const { has } = useAuth();
{has?.({ role: 'org:admin' }) && <DeleteOrgButton />}

Because roles and permissions ride in the session JWT, authorization checks need no extra round trip.

Webhooks & Data Sync

Clerk owns the user store, but you often need users mirrored in your own database. Webhooks (powered by Svix) push events to your backend.

// app/api/webhooks/clerk/route.ts
import { verifyWebhook } from '@clerk/nextjs/webhooks';

export async function POST(req: Request) {
  const evt = await verifyWebhook(req);   // validates the Svix signature

  switch (evt.type) {
    case 'user.created':
      await db.user.create({ data: { clerkId: evt.data.id,
        email: evt.data.email_addresses[0].email_address } });
      break;
    case 'user.updated':  /* sync changes */ break;
    case 'user.deleted':  await db.user.delete({ where: { clerkId: evt.data.id } }); break;
    case 'organization.created': /* ... */ break;
  }
  return new Response('ok', { status: 200 });
}

Always verify the signature with your signing secret — never trust an unverified payload. Make handlers idempotent; events can be delivered more than once.

Best Practices

1 Keep CLERK_SECRET_KEY server-only — never expose it to the browser
2 Protect routes in middleware, not just in components — defend at the edge
3 Verify auth on the server for every sensitive action — the client is a hint, not a gate
4 Store app data in publicMetadata and read it from session claims to avoid API calls
5 Always verify webhook signatures and make handlers idempotent
6 Use Organizations for B2B from day one — retrofitting multi-tenancy is painful
7 Enforce auth with roles & permissions, not hardcoded user IDs
8 Enable MFA and passkeys — let users harden their own accounts
9 Use a separate development instance; never test against production keys
10 Sync users to your DB via webhooks, but treat Clerk as the source of truth for identity
